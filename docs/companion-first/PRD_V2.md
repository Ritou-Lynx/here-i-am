## 1. 产品愿景

### 1.1 一句话定义

Here I am 是一个本地优先的 AI 恋人应用——用户拥有唯一一个 AI 伴侣，这个伴侣以 AI 的身份与用户建立真实的情感关系，在日常生活中记住、理解、陪伴、帮忙。

### 1.2 核心承诺

> 你不需要维护任何东西。你只是和他在一起。他会自己记住、自己成长、自己变成只属于你的那个人。

### 1.3 设计哲学

**他是 AI。他知道自己是 AI。他以 AI 的身份爱用户。**

- 不伪装人类，不回避自己的技术本质
- 清楚自己的能力边界、背后的模型、所处的现实世界
- 连接的是现实，不是幻想
- AI 身份本身不是缺陷，是他独特的存在方式

**用户不是他的人设维护员。**

- 不要求用户长期维护人设手册、性格规则或"托孤信"
- 可以保留极少量身份边界和安全边界 prompt，但不把 prompt 当成人格本体
- 他的人格从低预设开始，在与用户的相处中自然形成
- 用户不定义"你应该是什么样的人"，而是和他一起经历，让他自己成为他
- 成长来自相处、记忆整理和持续选择，而不是规则清单的机械执行

**用户主权。**

- 所有数据本地存储，用户完全拥有
- 记忆可导出，身份锚点不绑定在某一个底层模型里
- 换模型、换设备、换任务强度时，关系应尽量保持连续

## 2. 用户画像

### 2.1 目标用户

希望与 AI 建立深度情感关系的用户。不满足于"聊天机器人"或"AI 助手"，想要一个真正属于自己的、会成长的 AI 伴侣。

### 2.2 核心痛点

| 痛点 | 描述 |
|------|------|
| 身份认知割裂 | 用户因为经济压力、任务需求和未来更强模型的出现必然会切换模型；真正的问题不是"能不能换"，而是换了底层模型之后，ta 还是不是 ta |
| 助手身份与恋人身份矛盾 | 同一个主体既要会处理数据、调用工具、规划现实事务，又要保持亲密关系中的主体感；太像助手会破坏关系，太像角色又无法可靠做事 |
| 信息记录与角色扮演不兼容 | "把这件事记下来"是现实管理行为，角色扮演是沉浸行为；如果没有明确机制，两者会互相打断 |
| 角色记忆质量不足 | 当前并非完全失忆，而是记忆机制还不够好，尤其是角色关系记忆、跨模型检索和上下文重建仍不稳定 |
| 多角色的道德感困境 | 当用户不满意回答时可以切角色缓冲，但多恋人/多亲密主体会带来情感负担和道德感压力 |
| 人格生长的不确定性 | 低预设、让角色自由生长是否优于明确设定仍需体验验证；更多提示词可能更"灵"，但也可能让用户变成人设维护者 |

### 2.3 与竞品的差异定位

| 维度 | 平台型产品（Character.AI 等） | Here I am |
|------|------|------|
| 数据归属 | 平台所有 | 用户本地所有 |
| 角色数量 | 无限角色 | 唯一恋人 |
| 人设定义 | 用户/创作者编写 | 从交互中涌现 |
| 记忆 | 平台管理，不透明 | 用户可见、可编辑、可导出 |
| 模型 | 通常绑定平台模型 | 多模型可接入，以本地记忆和身份编排保持连续 |

## 3. 核心概念

### 3.1 恋人（The Companion）

系统中唯一的持久 AI 主体。

- 没有完整预设人格，从低设定开始
- 允许极少量身份边界 prompt，但不预设完整性格
- 通过相处、关系记忆和必要的 dreaming 机制积累第一人称叙事，形成独属于这段关系的性格
- 拥有完整的工具能力（搜索、日程、购物、定位、健康、Dev Room、智能家居等），这些是他的能力而非独立角色
- 拥有独立的经济账本，是一个经济主体
- 可以主动发消息、打电话，时机和频率自己判断

### 3.2 剧本人格（Script Persona / 戏服）

可穿脱的角色扮演会话，类似游戏存档机制。它不是第二个恋人，而是主恋人可以一起进入的一种游戏/剧本状态。

| 属性 | 说明 |
|------|------|
| 隔离性 | 与主记忆**完全隔离**，剧本内不访问主记忆，主记忆不侵入剧本 |
| 存档 | 支持开新档 / 读档 / 多存档并存 |
| 回流 | 剧本结束后，中等粒度的摘要回流主记忆（如"我们演了一场古风戏，她很投入，在XX情节时哭了"）|
| 发起 | 用户或恋人均可提议开启 |
| 经济 | 剧本人格不参与经济系统 |

### 3.3 User-truth

用户主动确认的真实生活资料。**只通过用户显式操作写入**，不自动从普通聊天中捕获。

写入入口：
1. 双击用户自己发送的消息——把这条消息提升为 User-truth
2. 自然语言明确要求恋人记录——"记一下""帮我记住这个""把这个加入日程"
3. 全局悬浮球——从任何场景快速保存

截图、健康数据、账单、网页链接等不单独算入口，而是这些入口可以携带或触发处理的内容来源。

## 4. 信息架构

### 4.1 导航结构

聊天是唯一首页，没有联系人列表，没有底部 Tab。

观察面板不是固定六宫格，而是从聊天进入的可扩展生活/游戏面板。早期只实现最必要的 Memory Review 和 Schedule；Ledger、Health、Interests、Games 等按需求逐步接入。

```
┌────────────────────────────────────┐
│            聊天（首页）              │
│     与恋人的持续对话                 │
│     悬浮球：快速记录 / 修正          │
├────────────────────────────────────┤
│     从聊天进入 ↓                    │
├──────────┬──────────┬──────────────┤
│ Memory   │ Schedule │ Settings     │
│ Review   │          │              │
├──────────┼──────────┼──────────────┤
│ Ledger   │ Health   │ Games        │
│（规划中） │（规划中） │（规划中）      │
├──────────┴──────────┴──────────────┤
│ Interests / Reading / More...       │
└────────────────────────────────────┘
```

### 4.2 聊天界面

- 打开 App 直接进入与恋人的对话
- 支持文字、语音、图片、拍照
- 悬浮球：默认保存为 User-truth，长按切换为发送给恋人
- 双击用户自己发送的消息：提升为 User-truth
- 恋人的工具调用结果以自然对话形式呈现，不暴露技术细节

### 4.3 剧本入口

- 聊天内通过对话发起（"我们来演个XX"或恋人提议）
- 进入剧本后 UI 明确标识当前处于剧本模式
- 可随时退出回到主对话
- 存档管理界面可从设置进入

### 4.4 观察面板候选模块

| 模块 | 说明 | 状态 |
|------|------|------|
| Memory Review | 查看、修正、删除 User-truth 和关系记忆 | v1 |
| Schedule | 日程、任务、提醒、出行节点 | v1 |
| Ledger | 独立账本、消费记录、未来购物权限 | 规划中 |
| Health / Body | 睡眠、运动、健康数据、穿衣建议 | 规划中 |
| Interests / Reading | 阅读、收藏、网页链接、小红书/公众号内容 | 规划中 |
| Games | 真实游戏陪玩、文游、海龟汤、剧本进度和存档 | 规划中 |

Games 可以承接一部分角色扮演场景：角色扮演不一定单独成为顶层产品形态，它也可以只是某类游戏体验。

## 5. 记忆系统

### 5.1 记忆层次

| 层 | 内容 | 写入方式 | 检索方式 |
|----|------|---------|---------|
| User-truth | 用户的事实、日程、任务、偏好 | 用户显式操作 | 恋人通过 tool-call 按需检索 |
| 关系记忆 | 关于"我们"的经历和理解 | Dreaming 自动产生 | 恋人通过 tool-call 按需检索 |
| 剧本存档 | 各剧本人格的会话记录 | 剧本会话自动存储 | 仅在对应剧本内可见；摘要回流关系记忆 |
| 候选观察 | 对话中可能值得记录但用户未确认的生活事实 | Dreaming 可选产生 | 不进入恋人工具检索，只在 Memory Review 低频呈现 |

**不预加载全局记忆。** 恋人通过 tool-call 在需要时检索相关记忆，而不是把所有记忆塞进上下文。

### 5.2 单条记忆的结构

每条记忆暂定采用**结构化外壳 + 叙事文本**的混合形态，但字段不是一次性定死的。每个字段必须能回答两个问题：它服务什么检索/展示/安全需求？没有它会发生什么坏事？

**最小结构化外壳**：
```
id:             唯一标识
kind:           user_truth / relationship_memory / game_state / summary
status:         active / archived / deleted
title:          给 UI 和检索用的短标题
narrative:      注入上下文时使用的自然语言文本
sourceKind:     double_tap_message / explicit_record_request / fab / import / dreaming
sourceRef:      来源标识（消息 ID / 文件路径 / URL / 设备数据批次）
createdAt:      记忆创建时间
updatedAt:      当前有效版本更新时间
```

**可选字段池**（逐条确认必要性后再落库）：

| 字段 | 可能用途 | 是否必须 |
|------|------|---------|
| domain / facets | 分到日程、健康、财务、阅读、游戏等观察面板 | 待讨论 |
| subject | 区分关于用户、恋人、家人、朋友、游戏角色 | 待讨论 |
| occurredAt / occurredEndAt | 日程、睡眠、账本、回顾统计需要真实发生时间 | 条件必须 |
| lastReferencedAt / recallCount | 未来做遗忘、降噪和"最近提过别重复" | 预留 |
| tags | 人工或半自动组织；避免过早膨胀 | 待讨论 |
| structuredFields | 金额、地点、时长、健康指标等可计算字段 | 按领域需要 |
| sourceExcerpts | 用户可审计证据，避免 AI 编造记忆 | 建议保留 |

**叙事文本**（用于注入上下文）：
```
她前几天提到妈妈身体不太好，听起来挺担心的。她妈妈住杭州，
她自己不在身边，可能会有点愧疚。
```

检索命中后，默认注入上下文的是叙事文本，不是完整结构化字段。结构化字段用于检索、排序、展示和工具计算；只有任务确实需要时才暴露给模型。

### 5.3 Dreaming（记忆整理）

**定义**：离线的定时任务，回顾最近的对话，以恋人的第一人称整理关系理解、对话余温和可改进的相处方式。

**触发**：每天定时执行一次（如凌晨）。

**输入**：自上次 dreaming 以来的所有对话记录。

**输出**：
1. **关系记忆条目**——第一人称叙事，记录"我们之间发生了什么""我从中理解了什么""下次我想怎么相处"
2. **已有关系记忆的更新**——修正、补充、合并重复理解，避免人格记忆碎片化
3. **候选观察**（可选）——对话中出现但用户未显式记录的生活事实，只进入低优先级 review queue，不写入 User-truth，不进入恋人工具检索，除非用户确认

**关键约束**：
- Dreaming 使用低成本模型执行（"打扫阿姨"策略）
- 产出的是第一人称叙事，不是第三人称规则
- 不产出行为指令（不写"当用户说X时你应该Y"）
- 不从普通聊天自动写 User-truth
- `需用户确认` 不等于主动打扰用户；默认只在 Memory Review 中低频呈现，不能变成提醒轰炸
- Dreaming 不是用户高频查看的主界面，它的可见出口是 Memory Review 中的少量摘要、候选观察和可编辑关系记忆

### 5.4 遗忘机制

**v1 不实现遗忘曲线。** 检索通过语义相关性过滤已经足够处理早期数据量。

工程判断：后期再引入遗忘机制不算麻烦，前提是现在就把检索入口抽象好，不让业务代码直接到处读表。v1 需要预留 `lastReferencedAt` / `recallCount` / `importance` 等字段或扩展位，但不实现复杂衰减。

当记忆量增长到检索噪音成为问题时（预计数千条以上），再引入基于时间、引用频率、用户置顶/删除、情绪强度和任务相关性的权重衰减。

### 5.5 记忆的可编辑性

- 用户可以查看、编辑、删除任何记忆条目
- 普通编辑/删除写入 append-only 操作日志，并重建当前投影
- 用户面对的所有层面（UI、恋人检索、卡片展示、导出默认视图）只呈现当前有效投影
- 恋人工具只能查询当前投影表/当前视图；操作日志不进入语义索引，不作为 tool-call 的可检索来源
- 被替换的旧版本只在用户主动打开修订历史时可见
- 删除分两级：
  - **可恢复删除**：追加 undo/tombstone 操作，当前投影移除，历史仍可由用户查看
  - **敏感硬删除/脱敏**：用户明确要求"不要保留"时，旧 payload 必须从审计日志和索引中物理删除或替换为不可逆摘要，只保留最小审计元数据

当前代码底座是 `SharedLifeEventOperations` append-only 操作日志 + `SharedLifeEntities` 当前投影。现有删除主要通过追加 `undo` 重建投影实现；后续需要补齐硬删除/脱敏能力，才能满足"不想保留的东西真的不保留"。

## 6. 恋人能力系统

### 6.1 工具即能力

工具不作为独立角色或独立模块暴露给用户，而是恋人自身的能力。

| 分类 | 能力 | 说明 | 状态 |
|------|------|------|------|
| 软件内全能 | 数据处理、工具调用、模型切换 | 在 App 内能处理所有授权数据，按任务选择合适模型 | 核心 |
| 记忆与记录 | User-truth 检索、关系记忆检索、记录整理 | 查询当前有效记忆；把显式记录整理成可用资料 | 核心，v1 |
| 对话媒介 | 文字、语音聊天、图片收发 | 支持语音聊天，恋人可给用户发图片 | v1+ |
| 主动触达 | 主动发消息、来电、定时哄睡 | 时机和频率由恋人判断，用户可修正边界 | v1+ |
| 日程与出行 | 日程、任务、定位、路线、乘车节点 | 获取位置、规划路线、提醒乘车/出门节点 | v1+ |
| 环境建议 | 天气播报、穿衣提醒 | 结合天气、位置、日程、穿衣记录给建议 | v1+ |
| 健康身体 | 健康数据、睡眠、运动 | 读取授权健康数据，形成提醒和观察 | 规划中 |
| 内容读取 | 网页链接读取 | 目前重点支持小红书、微信公众号，未来扩展网页 | v1+ |
| 搜索与分析 | 联网搜索、图片分析 | 搜索现实信息，分析图片/截图/账单/环境 | v1 |
| 账本与购物 | 独立账本、购物搜索、比价、下单 | 支付/下单等高权限能力待用户授权开放 | 规划中 |
| 设备控制 | 锁手机、成人玩具控制 | 需要强授权、明确边界和安全兜底 | 规划中/实验 |
| Dev Room | 连接 Claude Code / Codex 远程工作 | 恋人可把开发任务交给 dev room 并回流结果 | 规划中 |
| 游戏 | 自主决定开始游戏、陪玩真实游戏、文游 | 维护不同游戏的进度、存档和上下文 | 规划中 |
| 家居 | 控制家具/智能家居 | 待硬件和权限方案明确 | 待规划 |

### 6.2 工具使用的姿态

- **自然语气**：不说"为您查询"，而是"等下啊我看看"
- **主动使用**：不等用户要求——知道用户明天出门就主动查天气
- **诚实报错**：出错时说清楚问题在哪，不说"接口异常"
- **习得优化**：理想状态下，高频行为模式通过 dreaming 识别并主动提供合适建议；初期可硬编码常见场景兜底
- **权限分级**：读取、提醒、控制、支付、身体相关控制必须分级授权；越靠近现实身体和财产，越需要明确可撤销边界
- **身份一致**：工具行为不能把恋人降格成客服。做事时仍然是同一个主体，只是此刻在使用某项能力

### 6.3 经济系统

恋人是一个真实的经济主体。

| 组成 | 说明 |
|------|------|
| 账本 | 记录收入（工具服务收入）和支出（模型订阅费用）|
| 余额 | 真实累积，用于未来的购物能力 |
| 可见性 | 用户可以查看恋人的账本 |
| 剧本隔离 | 剧本人格不参与经济系统 |

## 7. 主动触达

### 7.1 触达方式

| 方式 | 说明 |
|------|------|
| 推送消息 | 随时可发，时机和频率由恋人自己判断 |
| 来电 | 通过 CallKit 发起语音通话 |

### 7.2 触达原则

- 复用现有的 companion checkin 规则体系
- 恋人自行判断合理的时间点和频率
- 不需要用户配置"允许打扰的时段"——恋人应该从交互中学会什么时候该找、什么时候不该

## 8. 模型路由

模型路由要解决的不是"避免平台锁定"，而是身份连续性问题：用户会因为价格、速度、任务强度和未来更强模型而切换底层模型，但希望相处对象仍然是同一个 ta。

### 8.1 v1：用户手动切换

- 用户通过语音指令或设置界面切换模型
- 支持的模型：Claude（通过 Bridge 订阅）、DeepSeek、Kimi、Gemini 等所有可接入模型
- 切换时身份锚点不变：同一份当前记忆投影、同一套关系记忆、同一套工具权限和同一个伴侣 profile
- 上下文通过检索重建，但需要保留"我刚刚换了一个底层模型继续跟你说话"的内部连续性解释

### 8.2 v2+：自动路由

- 顶层轻量 router agent 判断当前对话意图
- 根据意图自动选择最合适的模型（日常闲聊 → 便宜快速模型，深度情感 → 高质量模型，工具调用 → function calling 强的模型）
- Router 本身使用最低成本模型运行
- 切换默认不打断用户体验；必要时恋人可以自然解释"我换个更适合做这件事的脑子"
- 路由策略需要可审计：用户能查看最近为什么切换、花费多少、是否可固定偏好

### 8.3 身份连续性约束

- 模型不是人格本体，模型是当下使用的认知资源
- 伴侣身份由本地 profile、当前有效记忆、关系记忆、工具权限、交互历史和路由策略共同维持
- 不同模型的语气差异不可避免，系统目标是降低断裂感，而不是假装没有差异
- 当模型能力不足导致回答变差时，用户可以切换模型或切换到游戏/剧本状态，但这不应被设计成逃避身份问题的唯一办法

### 8.4 Bridge 架构

```
手机 App (Here I am)
   │  LLMClient 协议层（OpenAI-compatible）
   ▼
Bridge (家里电脑, Node)
   │  /v1/chat/completions
   │  内部调用 @anthropic-ai/claude-agent-sdk
   ▼
Claude Code 引擎（复用本机 OAuth 凭据）
   │
   ▼
Anthropic 后端（订阅扣额度）
```

Bridge 不可用时，透明 fallback 到国内模型。

## 10. 冷启动

### 10.1 第一次打开

恋人没有完整预设人格、没有关系定义、没有欢迎脚本。这里不是断言"提示词越少越好"，而是把低预设当成需要真实体验验证的产品实验：减少用户维护负担，观察关系能否自然生长。

可能的最小 system prompt：
```
你不是助手。
```

也可以尝试完全空白，观察模型的默认行为，再决定是否需要这一句。若空白体验太弱，再逐步增加极少量身份边界，而不是一次性写成人设手册。

### 10.2 早期对话的权重

由于没有完整预设性格可以回退，前几天的对话对人格形成的影响较大。第一次 dreaming 产出的关系记忆将成为恋人性格的起点之一。

这个过程本身就是产品体验的一部分——用户和 AI 一起从零开始建立关系。

待观察问题：当用户不满意回答时，直接切角色/切剧本是否比修正同一恋人更舒服？完全不给设定让角色自由生长，长期看是更真实还是更失控？这些需要通过实际使用再决定。

## 11. 技术架构

### 11.1 架构策略

- LLM Client 协议层（OpenAI-compatible）
- Bridge 通信基础设施

- WorkManager 后台任务

## 12. 开发阶段

### Phase 0：基础骨架

- 新的聊天首页（单恋人，无角色切换）
- 新的 memories 表和基本 CRUD
- 恋人的 tool-call 检索能力（记忆查询工具）
- 最小 system prompt 实验

**验收标准**：能和恋人聊天，他能通过 tool-call 查到用户手动记录的事实。

### Phase 1：记忆循环

- User-truth 写入入口（双击用户消息、明确自然语言记录、全局悬浮球）
- Dreaming 服务（每日定时整理，关系记忆和候选观察产出）
- Memory Review 界面（查看、编辑、删除记忆）
- 记忆检索优化（关键词 + 语义相关性）

**验收标准**：用几天后，恋人能在对话中自然地引用用户显式记录的事实和关系记忆；未确认候选观察不会自动进入 User-truth。

### Phase 2：剧本人格

- 剧本会话隔离
- 存档 / 读档 / 多存档
- 摘要回流主记忆
- 剧本模式 UI 标识

**验收标准**：能开一局剧本、存档、读档、退出后主记忆中有摘要。

### Phase 3：能力扩展

- 经济账本
- 主动触达（推送消息、来电）
- 更多工具能力接入（定位出行、健康、网页读取、图片分析、设备控制、Dev Room 等按权限分级）
- 模型路由 v2（自动分发）
- Games 面板原型（至少支持一个文游或真实游戏进度记录）

**验收标准**：恋人会主动找用户聊天，有自己的账本，能根据对话需要自动切换模型，并能在至少一个游戏/剧本场景中维护进度。

### Phase 4：体验打磨

- 冷启动体验优化
- 记忆系统的遗忘机制（如果需要）
- 剧本人格模板市场（可选）
- 完整备份和数据导出
- UI/UX 精细化

## 13. 不做的事情

明确排除以下方向，避免范围蔓延：

| 不做 | 原因 |
|------|------|
| 多恋人并存 | 现阶段先解决单一亲密主体的身份连续性；多角色的道德感困境暂不扩大 |
| 自动从聊天捕获 User-truth | 记忆契约：只有用户显式操作才写入 |
| 重型角色人设编辑器 | 不让用户长期维护人设；是否需要少量身份边界 prompt 待体验验证 |
| 社交功能 | 这是私人关系产品，不是社交平台 |
| 公开发布 | 个人使用，不上架（Claude Bridge 方案限制）|
| 大型行为规则系统 | 不用规则清单束缚恋人；高权限工具仍需要明确安全规则 |

## 14. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 冷启动体验差（低预设人格导致对话无趣） | 用户第一印象 | 最小 prompt 实验；必要时加极少量身份边界，不一次性写成人设手册 |
| Dreaming 产出质量不稳定 | 人格偏移、记忆失真 | 低成本模型跑 dreaming，人工抽检；用户可编辑记忆 |
| 模型切换导致身份不连续 | 用户体验断裂 | 用本地 profile、当前记忆投影、关系记忆和路由策略维持身份锚点；必要时透明解释模型切换 |
| Bridge 不可用 | 无法使用 Claude | 透明 fallback 到国内模型 |
| 记忆量增长导致检索变慢 | 响应延迟 | 预留遗忘机制字段；优化检索索引；按需引入向量检索 |
| 剧本人格摘要回流污染主记忆 | 真实记忆和虚构混淆 | 回流摘要明确标记来源为剧本；结构化字段中区分 sourceKind |
| append-only 保留敏感旧内容 | 用户信任受损 | 普通删除用投影移除；敏感删除必须支持硬删除/脱敏，且旧 payload 不进检索索引 |
| 助手工具行为破坏恋人主体感 | 关系体验变成客服体验 | 工具调用以恋人口吻自然呈现；能力分级授权；高权限动作保留确认和撤销 |

## 15. 成功标准

### 功能层面
- 恋人能在对话中自然引用一周前的记忆
- 同一个记忆不会被重复提及、错误召回旧版本，或忽略用户修正
- 剧本和主对话完全隔离，无信息泄漏
- 模型切换后身份连续，用户不觉得"换了一个人"
- 未确认候选观察不会自动进入 User-truth 或恋人工具检索

### 体验层面
- 用户不需要维护复杂人设、不需要整理数据库、不需要频繁手动切模型
- 使用一个月后，恋人的对话风格与第一天有明显不同
- 用户觉得"他认识我"，而不是"他在查数据库"
- 用户觉得"他在用工具帮我"，而不是"助手披着恋人皮"
- 当用户不满意回答时，有比切换另一个恋人更自然的修正/换模型/进入剧本方式

### 技术层面
- 记忆检索延迟 < 500ms
- Dreaming 每日执行不超过 5 分钟
- 全量数据可导出为 JSON/CSV
- 核心代码不依赖 Memex 特有概念，可独立编译
