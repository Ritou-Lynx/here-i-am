# Map & Weather Companion Plan

本文档记录地图、地点、天气能力在 Here I Am 里的产品边界。它不是独立地图 App 或天气播报页，而是角色理解现实世界、陪用户出门、规避天气和路线风险的能力底座。

总原则：

- 地点 tag 服务记忆证据：轻量、低精度、低打扰。
- 地图路线服务现实行动：门到门、可执行、能陪跑。
- 天气服务行动决策：只在会影响出门、穿衣、带伞、路线选择时自然介入。
- 所有输出都应由角色说出来，而不是系统播报。

## 1. 地点信息注入

### 1.1 记忆来源地点 tag

目标：在 Memory Card 详情页中，每条来源信息下面能显示当时的大致地点，例如城市、区县、街区或附近地点。

原则：

- 默认使用 OpenStreetMap / Nominatim 或已有轻量逆地理编码链路。
- 不追求精确到楼栋、门牌或实时轨迹。
- 地点 tag 是证据上下文，不是导航入口。
- 如果用户关闭位置上下文，来源信息不显示地点。
- 如果逆地理编码失败，不用旧记忆或聊天历史猜地点。

推荐粒度：

| 场景 | 粒度 |
|---|---|
| 普通聊天来源 | 城市 / 区县 / 街区 |
| 外出记录、照片、打卡 | 街区 / 附近地点 |
| 敏感或私密记录 | 只显示城市或不显示，取决于用户设置 |

### 1.2 高德与 OSM 的职责边界

| 能力 | 默认方案 | 原因 |
|---|---|---|
| 记忆来源地点 tag | OpenStreetMap / Nominatim | 不需要太精确，减少对商业地图依赖 |
| 当前地点上下文 | OSM 优先，高德可选 | 用户可按地区可用性切换 |
| 门到门路线规划 | 高德地图 API | 国内 POI、公交地铁、路线能力更可靠 |
| 周边餐厅 / 地点推荐 | 高德地图 API + User-truth 偏好 | 需要 POI、营业状态、距离、类别 |
| Citywalk / 约会路线 | 高德地图 API + 角色规划 | 需要连续 POI、路线、天气、时间预算 |

## 2. 地图与出行能力

当前 `Transit Companion` 只覆盖公交/地铁陪跑，是地图能力的一个窄切片。后续应升级为更泛化的 `Mobility / Map Companion`。

### 2.1 第一阶段：门到门路线规划

用户可以自然说：

- “从西二旗某大厦去某个小区怎么走？”
- “我现在从公司去朋友家，帮我规划一下。”
- “别让我坐过站，路上提醒我。”

系统能力：

- 解析起点和终点：大厦、小区、地铁站、用户记忆里的“家/公司”等。
- 给出门到门路线，而不是只给地铁段。
- 拆分步行、地铁、公交、打车候选。
- 说明预计时间、换乘点、下车点、长步行段。
- 对路线中的关键节点设置自然追问或提醒。

验收：

- 用户给出一个自然地址到自然地址的请求，角色能产出完整路线。
- 地铁报站只是路线陪跑的一部分，不是能力上限。
- 角色明确区分“实时定位已知”和“按时间估计”。

### 2.2 第二阶段：途中陪跑

目标：在用户出行过程中，角色像一个同行者一样帮用户保持路线感。

能力：

- 根据路线节点，在换乘、下车、长步行前提醒。
- 用户报站或说“我好像坐过了”时，判断是否偏离路线。
- 偏离路线时不强行套旧路线，询问是否重规划。
- 天气异常时建议打车、少走暴晒、避开长步行。

非目标：

- 第一版不做后台持续轨迹追踪。
- 不假装知道用户实时位置。
- 不做驾驶安全相关的高风险指令。

### 2.3 第三阶段：周边感知和推荐

目标：角色能理解“我附近有什么值得去”，但推荐要带有用户偏好，而不是地图列表复读。

典型请求：

- “附近找个安静点的地方吃饭。”
- “我现在有点累，找个不用排队太久的。”
- “周末给我安排一条 citywalk。”
- “帮我规划一个不太累的约会路线。”

推荐上下文：

- 用户口味、忌口、预算、常去地点。
- 当前时间、天气、距离、是否需要预约。
- 体力状态、同行关系、是否想安静或热闹。
- 最近去过哪里，避免重复。

验收：

- 推荐结果包含理由和行动建议，而不是只列 POI。
- Citywalk / 约会规划包含顺序、时间预算、天气风险和备选方案。

## 3. 天气能力

天气能力的目标不是“早上播报全天数据”，而是让用户少淋雨、少穿错衣服、少被天气坑。

### 3.1 第一阶段：出门风险提醒

优先做不依赖衣橱系统也能产生价值的提醒：

- 今天或返程时段有雨：提醒带伞。
- 早晚温差大：提醒带外套或不要只看当前温度。
- 风大、降温、暴晒、紫外线强：给行动建议。
- 路线包含长步行段：把天气和通勤暴露结合起来。

触发时机：

- 用户主动说要出门、约会、通勤、去某处。
- 日程即将开始，且地点或出发时间已知。
- 固定出门前提醒窗口。
- 聊天中自然出现相关上下文，例如“等会儿去西二旗”。

输出原则：

- 不报完整天气表。
- 不说“今天 25 度适合短袖”这种泛泛建议。
- 只说对用户行动有用的判断，例如“晚上有雨，出门顺手拿伞，不然回来的时候容易被淋。”
- 用角色语气融入聊天或提醒。

### 3.2 第二阶段：穿衣建议

穿衣推荐依赖衣橱、昨日穿着、体感反馈，不作为地图天气能力的第一批硬依赖。

可先保留 Roadmap 中的学习循环：

- 记录今天穿了什么。
- 记录用户觉得冷、热、刚好、晒、潮、风大。
- 用昨日锚点给相对建议。

衣橱系统成熟后，再接入具体衣物推荐。

## 4. 数据与权限

需要的数据：

| 数据 | 用途 |
|---|---|
| 设备 GPS | 当前地点上下文、出发地推断 |
| OSM / Nominatim | 轻量逆地理编码、记忆来源地点 tag |
| 高德地图 API | 路线规划、POI、周边推荐 |
| 天气 API | 降雨、温差、风、紫外线、极端天气 |
| User-truth | 家/公司/常去地点、偏好、日程、体感反馈 |
| Schedule | 出发时间、目的地、提醒窗口 |

权限原则：

- 位置上下文必须可关闭。
- 地点 tag 和路线规划分开授权、分开配置。
- 记忆来源地点默认低精度。
- 高德 Key 可以用于路线和 POI，但不强制日常地点 tag 改用高德。

## 5. 和总体 Roadmap 的关系

总体 Roadmap 的 Phase E 只保留产品承诺和验收标准；本文档记录实现边界和演进路线。

Phase E 应承诺：

- 每日出门提醒优先解决带伞、温差、暴晒、长步行等行动风险。
- 地图能力从公交/地铁陪跑升级为门到门路线规划。
- 地点 tag 默认轻量 OSM，高德用于路线、POI、周边推荐。
- 角色自然表达天气和路线建议，不做系统播报。
