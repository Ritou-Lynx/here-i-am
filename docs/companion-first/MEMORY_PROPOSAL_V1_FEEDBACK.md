# 记忆方案 v1 反馈意见

> 来源：主开发窗口（Lynx + Claude），2026-06-20
> 针对：MEMORY_PROPOSAL_V1.md

---

## 总体评价

三层架构（存储 + 检索 + 凝结）合理，迁移路径渐进，调研借鉴有理有据。以下是需要补充和修改的地方。

---

## 1. 关键缺失：用户编辑与删除权

这是已确认的产品决策（CLAUDE.md 第 3 条），方案里完全没体现。

原则：**append-only 降级为底层审计机制，用户面对的所有层面（UI、角色检索、卡片、导出）只呈现当前有效版本。用户修改即生效，角色永远不会读到被替换的旧版本。修订历史仅用户主动查看时可见。**

这会影响方案的每一层：

- **存储层**：Entity 需要支持"软删除"和"原地更新"。操作日志照常追加变更记录（审计），但 Entity 投影表直接改为最新值。需要在 §3 加一节"编辑与删除机制"。
- **检索层**：被删除/替换的 entity 的 embedding 必须同步作废或重新生成。融合排序只读当前有效 entity。
- **凝结层**：凝结时只读当前有效 entity，不读历史废弃版本。已生成的 summary 如果其 source entity 被删改，需要标记为 stale 并重新凝结。
- **导出**：导出只包含当前有效版本，干净的 Markdown，不带操作日志和修订痕迹。

---

## 2. 新增全局字段：情绪坐标

卡片最终要在 3D 空间呈现，坐标轴是愉悦度（valence）和唤醒度（arousal）。这两个值应该在 Record Organizer 写入时一并打分，因为情绪是记录时刻的上下文，事后推断不准。

建议在 domain schema 之外定义两个**全局通用字段**（所有 entity 都可以有，不属于任何特定 domain）：

```json
{
  "valence": 0.7,
  "arousal": 0.4
}
```

- valence：-1.0（极不愉快）到 1.0（极愉快）
- arousal：0.0（平静）到 1.0（高度兴奋/紧张）
- 两个字段可选，fact 类型（"我对花生过敏"）可以不打分
- 检索和凝结层不需要关心这两个字段，它们纯粹服务于 3D 可视化
- Record Organizer prompt 里加一条：根据内容语境推断情绪坐标，不确定时留空

---

## 3. 迁移阶段顺序调整

当前阶段 0（停血）和阶段 4（Record Organizer + 记录按钮 + 悬浮球）之间断档太大。停了自动捕获后，用户只剩 tool-call 一个写入入口，体验会严重退步。

建议：把"消息级记录按钮"从阶段 4 提前到阶段 1。这样用户在过渡期至少有两个写入方式（tool-call + 记录按钮），不至于只能靠说"记一下"。悬浮球可以留在后面。

调整后的顺序：
- 阶段 0：停血（关自动捕获）
- 阶段 1：domain + schema + **消息记录按钮** + 编辑删除机制
- 阶段 2：语义检索
- 阶段 3：凝结层
- 阶段 4：悬浮球 + 外部数据流

---

## 4. 凝结触发补充保底机制

阈值触发比定时好，但需要加一个保底：某个 domain 超过 7 天没凝结过，即使未达到阈值（10 条新增）也触发一次。避免低频记录的 domain（比如 clothing）永远不凝结。

---

## 5. Embedding 存储的扩展性

SQLite BLOB 存向量可以起步，但余弦相似度要全表扫描，数据量大了会慢。迁移路径里留个口子：未来可换 sqlite-vss 扩展或独立向量索引。现在不需要做，但 EntityEmbeddings 表的设计不要封死这条路。

---

## 以上意见的优先级

1. 用户编辑与删除权 — 必须加，这是产品决策硬约束
2. 迁移阶段顺序调整 — 强烈建议，影响过渡期用户体验
3. 情绪坐标字段 — 需要加，影响 3D 可视化核心功能
4. 凝结保底机制 — 建议加，实现简单
5. Embedding 扩展性 — 留意即可，不急
