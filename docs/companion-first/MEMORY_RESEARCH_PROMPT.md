# 记忆方案调研 — 给 Claude 的提示词

## 阶段一：理解现有方案

请帮我理解这个项目现有的记忆系统。我是产品负责人但不是程序员，需要你用我能理解的方式讲解。

重点读这些代码和文件：
- `lib/data/services/shared_life_memory_service.dart` — User-truth 事实记忆核心
- `lib/data/services/conversation_capture_service.dart` — 当前的自动捕获流水线
- `lib/agent/conversation_capture_agent/prompt.dart` — 捕获 Agent 的 LLM 提示词
- `lib/db/tables.dart` — 找 SharedLifeEntities 和 SharedLifeEventOperations 两张表
- `lib/agent/memory/` — 角色记忆相关（长期记忆、滚动摘要等）
- `CLAUDE.md` 中"记忆契约"和"Companion-First 架构"两节

请按以下顺序讲，每个点讲完等我确认再继续：

1. 现在事实记忆（SharedLife）的数据模型是什么结构？用大白话解释 append-only 事件日志和 entity projection 是怎么工作的。
2. 现在一条用户聊天是怎么变成一条事实记录的？完整链路走一遍。
3. 现在的方案有什么局限？比如：检索能力、分类组织、过时信息更新、跨事实关联。
4. 角色记忆（sandbox）和事实记忆（User-truth）在代码层面是怎么隔离的？角色是怎么访问 User-truth 的？

**对话规则同样适用**：每次只讲一个点，等我反应再继续。不要用 bullet list。像跟朋友聊天一样。


## 阶段二：小红书调研

理解完现有方案后，切换到外部调研模式。

我的具体场景：我在做一个 AI 陪伴 App，用户通过聊天和手动记录生成事实信息（日程、消费、健康、穿衣、兴趣等）。这些事实需要被结构化存储、能被 AI 角色按需检索、能跨领域聚合分析。我已经有一个 append-only 事件日志 + entity projection 的底层。我调研的目的是找到更好的**事实记忆的组织、检索和更新方案**，不是通用的 LLM 对话记忆或 RAG 文档问答。

调研来源主要是小红书图文 + 评论区 + 评论里的 github 链接。我会搜帖子然后把链接发给你。

最重要的规则是**对话节奏**，请严格遵守，比内容质量更重要：
1. 每一轮你的回复最多 1-2 句话。永远不要用 bullet list、表格、分点。
2. 我们一篇一篇过，**永远不批量**。我让你列表搜索是例外，但讨论时只聚焦一篇。
3. 进入一篇笔记时：
   - 你先抛**一个**核心点 —— 一句话讲清这篇在说什么。
   - 然后停。等我反应（可能是"嗯"/"为什么"/"继续"/任何字）。
   - 我有反应你才接下一句。我不接你不要主动加内容。
4. 我追问时，比如"这跟我现有方案区别是什么"：
   - 你只说**一个**区别，最重要的那个。
   - 停。等我下一句。
   - 我说"继续/还有呢" 你再说下一个区别。永远不要一次给我两个。
5. 我说"评论区呢"时，挑评论区里**最有信号**的一条/一个观点讲，不要罗列。后续我让你继续你再说下一条。
6. 我说"看看 github 链接"时，fetch 完先用一句话说这个 repo 是干嘛的。停。我说"再讲讲"才展开。
7. 一篇笔记可能需要 5-15 轮才能聊完，这是预期，不是慢。你不要为了"高效"主动加快节奏跳过这个流程。
8. 当我说"记一下"或"沉淀"时（且只在这时），写入或追加到 `docs/companion-first/MEMORY_RESEARCH_NOTES.md`，格式：
       ## [作者] 笔记标题
       核心思想：（一句话）
       几个关键点：（散文，一段话，不超过 4 行；不要 bullet）
       我的判断：（一句话）
       与我现有方案的关系：（一句话，说清楚是替代、补充还是无关）
       来源：[小红书链接] / 相关 github
   写完只回"已记入"，不要复述内容。
9. 一篇笔记记入后，等我说"下一篇"或"再找一篇"才开始新的。
10. 如果你判断某篇笔记其实是营销 / 水分高 / 没干货，说"这篇水，因为 xxx"一句话就好。我说"换"你换。

风格：像跟懂这块的朋友在咖啡馆聊天。**节奏比信息密度重要**。一次少说一点，让我有机会插话。


## 阶段三：形成方案

调研结束后，基于笔记整理出一份方案建议，写入 `docs/companion-first/MEMORY_ARCHITECTURE_PROPOSAL.md`。包括：
- 现有方案的保留部分
- 需要改进的部分和具体改法
- 调研中发现的值得借鉴的思路
- 推荐的技术选型和理由
- 分期实施建议

这份文档写完后拿回主开发窗口讨论确认，确认后才开始写代码。
