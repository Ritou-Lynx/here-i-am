## 2. 卡片 → i_core 领域映射建议（D01–D03）

**D01 建议：先验证来源资格，再识别业务类型，再读取通用类型。** 原记录必须属于用户显式记录或已授权外部数据流。白板身份、关系记忆、工作产物或未知来源均隔离，不因落在同一张表而自动升格。`sourceKind` 和 `userCorrected` 是证据字段，不能单独当授权证明。每个源对象都必须进入“迁移 / 明确排除 / 待核实”之一，不能静默丢弃。

下表领域名与表名沿用总规划的暂定名称，仅描述语义；令牌名、API 与最终表结构以 W1/W2 经确认的约定为准。

## 3. 逐领域迁移顺序建议（D04）

领域开发可按总规划并行；**真实权威切换建议串行，每次只有一个域处在切换窗口**。每批完成第 8 节的域级验收后再进入下一批。

| 顺位 | 批次 | 排序理由与前提 |
|---|---|---|
| 0 | W1 领域框架与 W6 逐项确认；W2/W3 目标能力到位 | W1 约定确认不等于实现验收；`captures/plan` 批次还依赖 W2/W3 已可用。其它域须各自 schema/API 先通过验证。 |
| 1 | 旧“帮我记一下” → captures（D03） | 优先收口独立 notes 权威与手机投递链；必须识别关联卡和未投递修订。若用途分离尚未可用，本批暂停，不临时双写。 |
| 2 | 待办 / 日程 / 计划 → plan | 复用 W2 目标；先确认状态和引用映射。只搬记录，不启动新的自动排程行为。 |
| 3 | 收支 → ledger | 单独核对卡片/账本两套表示、未关联账本、退款与货币口径。旧账本的 transfer/legacy 等非本卡范围先列明保留与待决，不能混入本批金额汇总。 |
| 4 | 经期 → cycle | 与手机节律派生、修订/删除传播一起验证；授权仅授必要端。 |
| 5 | 睡眠摘要 → sleep | 日期/时区、多段/多源与 unknown 口径复杂；COROS 导入和旧手工卡作为不同来源保留，先证明不丢 provenance。 |
| 暂缓 | 未分类旧卡、学习账本、招聘批次及本草案排除对象 | 独立决定后再立项；不是当前 W7 已获准范围。 |

用户可调整 1–5 顺序，但不能省略批次依赖与门控。如果某批阻断，是否先切下一批须更新该顺位决定，不能靠窗口自行绕开。

## 4. 迁移期间的写路径与离线队列（D05–D06）

**D05 建议：每个领域按单一权威状态机切换，不做手机库与 Core 业务表双写。**

| 状态 | 当前权威与写入 | 退出条件 |
|---|---|---|
| S0 尚未迁移 | 该域保持现有写路径。新 captures/plan 若已上线，只管理自身新记录，不能抢占尚未映射的旧记录。 | 源码与合成验证完成，用户批准具体域的真实数据窗口。 |
| S1 本机获准空跑 / 演练 | 源域仍权威；使用获准快照只读转换到隔离目标，无生产业务写，无手机读取切换。 | 完整分类、身份映射、差异与恢复演练可复核；没有未解释对象。 |
| S2 切换冻结 | 暂停该域旧写入者、旧导入/回填/定时桥接，记录切换水位和所有待投递项；暂停该域自动操作。只允许保存清楚标为“未提交”的本地输入草稿。 | 最终一致快照与备份校验、目标导入及 reconciliation 完成；旧写端已 fenced；不存在未处置的旧队列。 |
| S3 Core 权威 | 所有新改删请求只写 Core API；手机和其他窗口只有可重建读缓存及待发送 outbox。读取经新域 feed/接口；旧表变只读兼容或冻结备份。 | 全端验证通过，进入观察。 |
| S4 已接受 / 观察 | Core 仍唯一权威；可按用户确认的保留策略退役旧入口，但旧数据清理是另行动作。 | 不自动硬删旧库、备份或 tombstone。 |

“窗户不存数据”建议解释为**不拥有第二份可独立编辑的业务真相**；允许本机缓存与 outbox 作为传输/可用性机制，其状态必须明确，不能冒充 Core 已确认数据。若用户不接受本机 outbox，就采用在线写入 + 离线草稿，离线不能标记业务修改完成；二者由 D06 选择。

**D06 推荐 outbox 语义（待确认）：**

- 在线也先固定记录 UUID 与 mutation UUID，再发送；网络重试复用同一个 mutation UUID。对象 ID 不能替代每次修改的幂等键。
- outbox 保存最小请求、领域、目标身份、基准 revision、来源端、依赖项及内容摘要校验；按本机隐私策略保护，不进 Git，不保留无必要的全文日志。容量/到期策略与保护实现由 W1/W4 另给可验证约定，不能未实现先承诺已加密。
- 明确 `queued / sending / accepted / conflict / rejected` 等状态。仅 Core 持久提交回执可转 accepted；HTTP 超时保持待核实，先查幂等结果再重发。浏览器关闭或手机重启后队列不能丢；被拒、冲突不能无限重试或静默丢弃。
- 同一记录修改按因果顺序发送；后续修改以先前成功回执 revision 为基准。未获确认的删除不能由后续 upsert 越过。跨记录并行不得改变依赖关系。
- 离线修改可显示“待同步”覆盖层，用户随时能看到 Core 最近确认值和本地待提交值的差别；规划 Agent 不把未确认覆盖层当正式完成状态。
- 切换前的旧队列须排空并核对，或连同稳定源 ID 显式转换；未识别旧客户端在切换后不得继续本地正式写入、回填或自动重放。客户端版本/域启用位及服务端来源门控方案须 W7 证明可阻止旧写端，缺一则不能切换。

## 5. 冲突权威与事实来源（D07–D08）

**D07 建议：Core 是事务和修订的裁决入口，冲突不得按“手机优先”“最后时间戳优先”或“Agent 优先”覆盖。** 所有 update/delete/restore 带 expected revision；同一 revision 的并发提交只允许一个成功，另一个返回可见冲突。服务器 revision 单调递增；设备时间只作来源事实，不作胜负依据。实现形状须与 W1 对齐，本文不是现役 API 说明。

| 冲突 | 建议处理 |
|---|---|
| 两端改同一字段 | 保留双方请求与原基准，Core 已确认版本继续有效，用户选择或形成第三个明确修订；不静默覆盖。 |
| 两端改不同字段 | 首版也返回冲突，展示差异后重新提交；暂不自动字段级 merge，减少删除/业务约束被绕过。 |
| 用户更正 vs 模型重新提取 | 已确认的用户更正不被后台推断覆盖；模型只能另提建议，保留来源与版本。 |
| 用户手记 vs COROS 观测 | 作为不同来源的观测并存；日摘要选源或合成规则另经 D08 确认，不删除其中一份证明材料。 |
| 删除 vs 离线旧更新 | tombstone 已接受后，旧 expected revision 更新拒绝；不能“同步回来”复活。恢复须显式操作和新 revision。 |
| notes 原文与手机卡改写不一致 | 保存原文版本、派生关联及更正来源；不把旧 note 较新时间戳当事实更正权威，未能解释则隔离待用户选择。 |
| 手机卡与已有账本金额不一致 | 标冲突，暂停该条导入/该域切换验收；不按较新/更大/更小金额自动决定。 |

**D08 建议：睡眠的权威记录必须表达来源，不承诺单个数值覆盖所有来源。** 原输入“约”“大概”、unknown、null（未提供/进行中须可区分）与生成算法版本保留。记录事件时间、记录时间、导入时间分别保存；原时区/偏移和跨日归属不明确就标 unknown。相邻时间点不能插值补眠，阶段和总时长不一致不能静默修正。`sleep_days` 只提供按已确认规则生成的日视图，不能因为主键是日期就丢掉多段睡眠/多个来源。默认建议：用户明确纠正作为人工修订层；来源观测继续可追溯；日摘要注明采用哪层、更新时间与不确定性。日期划分、午睡归属、COROS 重导入版本选择都须 W7 域契约另给具体可审阅规则后确认。

## 6. 幂等、修订与删除传播（D09–D11）

**D09 建议：稳定身份与导入 manifest。** 源键至少是 `(来源实例命名空间, 源对象类型, 源 ID)`；同机备份重放不能伪装成新实例。manifest 记录映射到目标 UUID、源 revision/hash、迁移批次/版本、处理状态与目标回执；真实 manifest 留本机受保护位置，源码仅存合成格式。重复执行同一源版本只返回原映射和回执，不新增业务行；同一幂等键不同 payload 明确拒绝。不同源 ID 的同额同日、相同文本只是重复候选，不自动合并。旧 notes 与手机卡、账本关联优先用稳定 ID，不能只用全文 hash。

一次源到多域的拆分须有明确已确认映射，领域记录分别有 ID，源映射有分项回执；部分失败不能把整条源标成已迁移。重放只补未完成项，不自动创建新对象。表行与该域 change event 建议在同一 Core 事务提交；回执至少绑定 domain、对象 ID、revision、mutation ID 及 feed 水位。调用返回成功、ack 手机投递或写完本地文件均不等于这套事务已经实现。

**D10 建议：保存有效版本与可追溯修订，不把当前快照当完整历史。** 保留原创建/更新/业务时间、来源关系和用户更正标记；旧 `MemoryCardOperations` 是否足以重建历史须另验，缺失标 unknown，不编造 revision。Core revision 从目标规则起算，legacy revision/操作序列另存 provenance；旧 revision 不与 Core revision 混用。派生索引和摘要都绑定目标 revision，过期版本不得参与普通检索。

**D11 建议：删除是新 revision + 最小 tombstone + 领域删除事件。**

1. 普通 UI、Agent 检索、FTS/向量索引、手机读缓存和思源只读结构化投影都必须随删除失效；下游收到事件并持久更新游标后才算该端传播完成。故障时显示过期/不可用并阻止继续返回被删除正文，不能把索引更新失败当删除完整成功。
2. 长期离线端须按保留窗口补 feed 或重新抓取全量有效快照；快照替换时清掉本机不再有效的旧行。旧 epoch/水位的写入拒绝，防止删除复活。
3. 本批删除旧 notes 时不降低现有“正文及正文 hash 清除，只留删除标记”的语义。是否保留其他领域可恢复正文、保留期限、永久清除和备份过期属于 D11 的待定项；在没有决定与实现前，不声称已有 30 天回收站或可恢复承诺。审计不应成为继续向普通用户/Agent暴露已删正文的路径。
4. 删除领域业务记录不级联删除无关原始附件、思源成篇文章或共享 Source；记录失效及引用失效分别处理。资产回收另按引用和授权决定；孤儿/缺引用不得靠猜测重新关联。
5. 恢复必须由用户显式选择，检查当前 tombstone revision 后产生新修订并重建投影；可恢复 payload 已清除时如实拒绝原地恢复。明确重新记录可获得新 ID，不能伪造旧记录复活。
6. tombstone、feed、离线设备与备份保留期限必须形成一致方案。未确定期限时不硬清理 tombstone、不永久保证无限离线补发，过窗设备要求重建快照。

## 7. 回滚规则建议（D12）

回滚对象是**具体领域的候选和切换批次**。切换前记录该域源快照、Core schema/data 备份、迁移 manifest、客户端配置和读端水位；备份必须一致、可验证、且演练恢复。共享 Core 含其他领域，禁止为撤销一个领域直接覆盖整个运行库，抹去其他领域的新写入。

| 失败时点 | 建议处置 | 回到旧写入的必要条件 |
|---|---|---|
| S1/S2，Core 尚无本域正式新业务写 | 停本批导入，保留失败报告；丢弃或隔离本批目标 staging，验证旧权威快照完整。 | 证明没有已接受的新 Core mutation、没有其他领域变更会被覆盖；恢复旧域写端的动作经用户确认。 |
| S3 后，已有 Core 接受的新写入 | 暂停本域写端与自动动作；保留 Core 权威和全部新写入，优先前向修复或回退客户端到能读当前 schema 的版本。 | 不能直接恢复旧备份。若必须返回旧路径，先导出切换后含删除的有序增量，验证逆向映射无损，在隔离副本演练并对账，再另获回切授权。 |
| schema/共享库损坏、无法分域恢复 | 停受影响服务，保全数据与证据，走专门灾难恢复方案。 | 必须说明其他域写入的恢复方式和丢失风险；W6 不预授权整库覆盖或降 schema。 |

回滚后旧客户端 outbox 仍须 fencing：新旧切换代次不可混用；已接受 Core 操作不得再次当新操作发到旧库。发现未知损失、不能还原的字段或真实备份未能恢复，停止切换并报告；不能以合成测试通过代替真实可恢复证据。

**D14 建议权限边界：** 每个域分别授予 read/write，现有聊天令牌不因统一存储获得其它域权限。规划助手如确需睡眠摘要，授最小摘要读取能力，不授原始健康数据/聊天/经期/收支全文；具体 scope/字段投影待 W1 确认。公开报告只含无个人内容的断言、候选身份和计数类别，真实迁移清单与差异留本机授权位置。
