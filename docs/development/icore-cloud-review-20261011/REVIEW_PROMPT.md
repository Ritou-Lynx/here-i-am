# 给独立云端模型的审查任务

请独立调查此目录描述的 iCore 切换反复失败。不要继承“审核通过所以应该没问题”的结论，也不要再创建一套更长的审批文档代替定位。

## 目标

解释为什么早期大量自动测试与两窗审核通过，实际入口仍反复失败；找出当前 r08 在真正 Run 前后仍可能失败的具体条件；提出最短、可验证且不伤害真实数据的完成方案。最终目标是完成 iCore 切换及 Claude/ChatGPT MCP 可用性，不是继续无限扩展维护框架。

## 材料与优先级

先读 README、INCIDENT_REPORT、SOURCE_MAP、evidence-summary，然后读 snapshot 中的真实执行链。仓库根目录是维护基线，并非最新私有候选；不能只扫描顶层 tools 后宣称审查完成。

对运行事实按三个等级标注：可由公开源码复现；只有本机摘要/回执哈希支持；尚未知。不能把哈希本身当成未公开回执的独立证据。

## 必查问题

1. entry/controller 是否在每个失败点提供足够且脱敏的阶段/错误信息？如何保留原始错误类型，又不输出配置/令牌/真实路径？检查 catch、finally、子进程 EOF 和资源释放。
2. 117 项 artifact 检查为什么漏掉额外 60 项基线？能否从实际执行读依赖生成同一套前置检查？检查 ACL、owner、父目录、文件身份、TOCTOU、只读租约和写入顺序。
3. SID 修复是否完整？其他账户表示、Task XML 导出、COM 标准化、登录类型、安全描述符是否还有同类“字面相等”缺陷？
4. 当前只读适配器与真实入口从哪一行分叉？检查后续 322 行身份、锁、包切换、任务更新、Run、P3/P4、收容与逆向路径。指出哪些不能由适配器通过推出。
5. 分析生成依赖图：原始四配置→派生配置→主计划→recovery/P4→备份策略→login→facts→任务模板→策略→binding→approval。检查自引用、旧 hash 语义、两个动态槽、实际落盘读回、模板与实际导出是否一致。
6. 检查一次性 attempt 与 Run 两个计数：在哪些阶段消耗、失败后如何保持不确定性、旧 attempt 保留、新 attempt 不存在、总 Run 上限是否真的被所有路径执行；不能以没 Run 为理由复用入口。
7. 检查备份、恢复、正常关机后登录以及无闪窗方案；不要继承旧代次恢复证明，不要让休眠健康状态替代活动健康状态。
8. 区分必要安全边界和流程负担。哪些 exact-byte 审核可以一次性由机器完成，哪些变化真的需要真人新决定？为什么一个账户表示修复需要如此长的派生链？给出可实施的简化，而非移除身份/数据保护。
9. 现有 CI 有哪些测试只覆盖合成模型、遗漏 Windows 真实语义或未覆盖后来增加的私有代码？设计最小的隔离故障复现；不要重复整个已有大测试集。

## 输出要求

- 按 P0/P1/P2 排序的具体发现：文件+行号、触发条件、现有证据、影响、最小修复与验证；不得把推测写成已发生。
- 一页清晰依赖/状态图；指出最早失败点与必须串行的步骤。
- 说明已知三个阻塞之外，是否还存在未排除的生产阻塞。没有发现也说明审查覆盖边界。
- 区分“代码修改”“合成测试”“需要本机只读补证”“最终真人动作”。
- 给出最短完成步骤和条件式时间估计，说明未知项，不保证分钟级上线。
- 可在合成环境写最小补丁与测试，独立任务分支提交。不要修改当前生产批准、不要以替换哈希绕过保护。
