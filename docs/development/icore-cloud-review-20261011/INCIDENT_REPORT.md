## 4. 已确认的阻塞条件与修复

### 4.1 私有文件 ACL 前提没有闭合

派生备份配置初始允许 owner、SYSTEM、Administrators 三个 SID；控制器要求 owner+SYSTEM。另有 P0 基线文件和 55 个基线源码文件继承未保护 DACL，而原生私有读租约要求保护 DACL。最初 117 项绑定检查没有覆盖控制器额外打开的 60 个基线文件。

已针对叶子文件修正 DACL，记录内容哈希、owner/group 和父目录不变；额外 60 项已完成本机原生读租约核对。曾尝试完整 SetAcl 时遇到 SeSecurityPrivilege，后改为只修改 DACL。

这是确定的契约不一致与漏检。由于统一 catch，不能证明它恰好是某次失败的第一条异常。审查应检查同一文件为什么存在多套不同的 ACL 规则，以及权限修复范围是否被正确约束。

### 4.2 attempt 父目录未创建

只读诊断通过控制器 63–110 行后，发现 activation 父目录不存在。第 111 行调用 FreshDirectory(attempt)，而原生 helper 要先打开所有父目录，不递归创建它们，因此存在必然失败的前提。

之后只创建缺失的空父目录并设置要求的私有 ACL。如今它包含已消耗的旧 attempt；新流程只能检查“新 attempt 不存在”，不能再要求整个父目录为空。

### 4.3 Windows Task Scheduler COM 返回账户名而非 SID

原 r07 控制器 314 行直接比较：

```powershell
$expected.Principal.UserId-cne$owner
```

真实的、尚未注册的 COM TaskDefinition 接收 XML 后，Principal.UserId 返回账户名；XML 中是 SID。NTAccount→SID 后两者相同，其余 Enabled/Hidden/RunLevel/LogonType/Actions.Count 五项满足要求。这是同一账户的表示差异，不是身份变更。

r08 只替换为：

```powershell
(Convert-TaskSid ([string]$expected.Principal.UserId))-cne$owner
```

沿用已有 Convert-TaskSid helper；未放宽其他谓词。9 项专项涵盖真实未注册 COM 同账户、直接 SID、不同 SID、非法身份及其余五项拒绝。修复后只读前置检查通过 321 行。它不覆盖 322 行真实入口自身份检查及后续执行阶段。

### 4.4 准备链中的附加修正

配置写入器此前需要从“检查写入输入”改为“检查实际落盘读回”；已修正。最新 r08 核对包含原始四份配置不变、core 只变 manifest 引用、MCP 原字节不变、备份配置的两个 SID、登录关联和策略/plan 绑定。仍需云端独立审查这些断言是否覆盖完整依赖，而非照抄通过结论。

## 6. 为什么一直暂停：事实与待检验判断

具体暂停有真实触发点：XML 实际导出差异、ACL 前提不匹配、父目录缺失、COM 身份比较、源码变化使旧精确批准失效、旧一次性 attempt 已消耗。最新 r08 不是“还没写完代码”，而是离线候选等待新的生产决定；用户现在要求先云端审查。

但暂停不能解释成全部合理。**流程本身也需要审查**：

- 原始异常被通用拒绝码掩盖，导致通过再次执行逐步发现基本前提；
- 测试与静态审查没有共同覆盖“真实配置 + ACL + 文件树 + COM 规范化”；
- 私有工程代码增长，却缺少清晰、可复现的公共候选与统一状态模型；
- 每次小变更引发大量摘要、哈希与交接材料重建，成本高，仍可能漏掉关键契约；
- “通过”有时只代表某个准备层，用户却一直等待最终切换，进度语言不够清晰；
- 执行窗口曾使用用户认为成本过高的 Astra；现已改为 GPT-6.1 Sol。没有可靠账单归因，不量化哪次工作消耗了多少额度。
