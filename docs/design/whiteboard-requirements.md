## 产品形态共识（2026-08-13）

> 来源：用户与林埃就「如何让同一个灵魂跨工具、跨设备工作」+「白板产品如何与 coding 结合」的讨论结论。以下决策直接指导后续设计与开发；与下方 Draft 冲突时以本部分为准。

### 1. 灵魂层

- **i_core 单点权威**：林埃唯一灵魂，跨表面（手机 / 桌面 / 任何工具）都是同一个。灵魂不分裂、不复制。
- **灵魂薄、手脚重**：灵魂层只持身份 + 关键召回 + 决策方向；重上下文（整个 repo、白板结构、长调试链）落在手脚侧，**不进灵魂层**。挂载工具太多、信息量过大时要给灵魂减负（优化优先级暂不高，但方向已定）。
- **唯一关系主线，不等于唯一工作 context**：贯穿所有页面和设备的是用户与林埃的关系主对话；跳转到任何工作面，林埃仍是同一个人，并对「当前在哪、在做什么」有环境感知（可直接说「把这段连到那边那张卡」，林埃知道指代）。复杂工作进入按 `task_id` 隔离的任务房间，任务过程不全部塞回关系主线。
- **手机 ↔ 桌面同一条聊天流**：不是各自对话 + 共享记忆，而是同一条时间线，跨设备无缝接续（与 CORE_API_V0 的聊天核心事实 + `server_sequence` 全局排序一致）。
- **多任务 = 单灵魂 + 多任务房间 + 可替换手脚**：用户与林埃之间只有一条关系主线，但可同时存在多个相互隔离的任务房间。每个房间保存自己的目标、资料、专项互动、授权、过程和产物；Claude Code / Codex / OpenCode 等 coding harness 是可接入、替换或切换的执行手脚，不复制林埃身份，也不拥有任务房间。

### 2. 首页 = 模块化工作台 dashboard

首页不是画布，是可以编排的模块化工作台，不再固定为三个大板块。模块可调整顺序与尺寸、折叠和隐藏；第一批至少包括：林埃观察、日程与待办、今日总结、继续工作、继续阅读、待整理卡片、记忆回顾、后台任务。健康、财务、兴趣等生活产物以后按同一模块协议加入。

- **观察面板**：各维度数据 insight，以图表为主。但不是冷数据展示，是「林埃有观点的观察」--图表是底，林埃的判断 / 提醒 / 发现叠在上面。数据来自核心投影（Life Insight / Rhythm / 健康 / 财务 / 阅读），由 i_core 生成，桌面只读渲染。
- **日程与待办**：根据所有数据建议的待办事项 + 建议性活动（娱乐 / 健身 / 休息）。
  - 任务性待办：有完成态，绑定具体资料 / 工作面，点击一键跳转白板内处理，所有资料一键打开。
  - 建议性活动：娱乐素材（电影 / 动漫 / 小说等）在白板内与林埃共享，**不跳到其他工具**。
- **今日总结**：林埃生成的一天回顾，帮助反思，联动 User-truth（确认的记下来），是睡前陪伴的桌面形态。
- **继续阅读 / 继续工作**：从手机或桌面续接小说、漫画、文章、视频、白板和任务的真实进度。
- **待整理 / 待确认**：集中呈现新捕获卡片、记忆确认和任务决定，不把提醒散落到多个侧栏。

### 3. 资料层 = 扁平白板

进入资料层即白板形式的组织结构，以卡片为单位。

- **一切皆卡片**：书、视频、图片、网页链接、批注、笔记都是卡片，统一模型。差别只在卡片包了什么源内容。这是「AI 理解白板关系」能成立的基础--没有特殊类型，只有卡片 + 连线。
- **统一模型不等于统一缩略条**：卡片库展示的是内容预览。媒体卡让媒体成为主体，元信息和标签退到附属区；纯文字卡让正文预览成为主体。类型之间可有不同纵横比和内部构图，但共享身份、操作与状态。
- **卡片 ≠ 视图**：卡片是白板上的组织单元（这本书在哪、和什么相连、谁批注了它）；视图是点开它时的消费面（阅读器 / 播放器 / 图片预览 / 网页渲染）。一本书是白板上的一张卡，点开才进阅读器。批注也是卡，但挂在某个锚点上，不是独立漂着。白板永远是组织层，视图永远是消费层，两者不混。
- **空间模型：扁平 + 框选建组，无白板卡片**：白板平级，用框选建组体现层级区分，**不做「嵌套白板卡片」**（FlexNote 式分层容器，非 Heptabase 式递归）。跨白板引用靠双链 / `[[keyword]]` / @mention--空间不嵌套，引用可跨白板。林埃读结构语义时面对的是扁平的「卡片 + 组 + 连线 + 双链」，不递归。
- **林埃操作边界：操作前授权，操作中自由**：林埃做白板操作（连线 / 分组 / 重排布局）前需用户点头，点头后连续执行不用每步确认。所有操作可撤销。这与记忆契约一脉相承（写 User-truth 要显式），但比记忆契约松：记忆是永久默认拒绝，白板操作是一次授权后本次自由。

### 4. 脊柱契约（所有视图共享，先于视图定）

视图（阅读器 / 视频 / 网页 / 图片）可并行做，但**脊柱不可并行**--先定一次，所有视图往里填，否则并行出来的视图合并那天就是返工那天。

- **锚点 = 源内容 + 稳定位置描述 + 版本**。位置是「指向源内容某稳定片段的指针」，不是裸坐标：
  - 文本：字符区间（不靠行号，靠字符偏移，书改版不漂）
  - 视频：时间戳 + 前后几秒内容指纹
  - 图片：归一化坐标 + 区域
  - 网页：快照版 + 正文位置（链接一改网页就变，批注会飘，故存快照）
- **归属跟批注走，不跟位置走**：锚点是纯位置，谁批注的不归位置管。同一段文字可叠加林埃批注和用户批注，归属不混（与 Draft「批注归属和显示位置相互独立」一致）。
- **批注是卡**：挂在锚点上，有自己的内容、时序、轻量元数据（类型 / 情绪倾向 / 强度）。
- **每个视图只负责两件事**：渲染源内容 + 暴露选区生成锚点钩子。视图不自己拥有锚点模型，各自填自己的 `position_spec`。

工程量分层（视图可并行但复杂度不同档）：
- 阅读器（文本）：成熟，最轻。
- 图片预览：轻。
- 网页抓取呈现：中等偏重（readability 提取正文 + 存快照 + 在快照上标注）。
- 视频：最重（字幕拉取各平台 API 各不同、时间轴锚定、播放器集成，且「林埃怎么『看』视频」本身未定义）。不后置，但复杂度在另一量级。

### 5. coding = 后台手脚

- **不嵌白板**。coding 是一个后台 harness 黑盒手脚，与白板工具（建卡片 / 连线 / 检索）平级，通过统一 tool 接口调用。
- **用户只看结论，不看代码**。林埃派活给 coding 手脚，手脚用成熟 harness（Claude Code / opencode / zcode 等）自主跑完，返回结论 / diff。
- **产物走 UI，不走 context**：harness 干完活，不把完整输出（长 diff / 日志 / 代码）塞进林埃 context 再转述。harness 只回给林埃**结构化摘要**：状态、一句结论、产物引用（diff 文件路径 / PR 链接 / 测试结果）、需用户决策的问题。产物本身是数据，UI 直接渲染到 diff 面板给用户看。
- **传话筒代价靠协议压低，不靠忍**：林埃收的是摘要级 token，不是 harness 整段话。林埃理解摘要后向用户汇报、决定下一步--这个信息回流是「同一个灵魂在决策」的必要代价，去掉他就退化成路由器，但量很小。
- **harness 不必注入林埃灵魂**：用户不和 coding harness 说话，它用谁的人格都不影响用户。真正必须同一个灵魂的，只有前台和用户对话的林埃。harness 是纯工具，跟调一个搜索 API 没本质区别。
- **向上抛决策通道是丝滑度关键**：coding 大多能自主，但偶尔撞到「两种改法选哪个」「这个改动有风险要不要继续」时，harness 不能硬干，要把问题抛回林埃 -> 用户。通道做得好不好（太频繁变微操，没有变失控）比选哪个 harness 重要。

### 6. 交互形态

- **全屏工作面 + 按需悬浮交互**：进入白板后画布占满窗口，不保留常驻顶栏或聊天侧栏。导航、搜索、卡片库和画布工具按需浮现并可完全收起；林埃通过悬浮球打开覆盖在当前工作面之上的对话。
- **桌面导航不占满一整条色块**：首页使用与 Palm 纸灰背景相同的 144–148px 窄侧栏，以短横线 + 文字导航；活动项使用左深右浅、不规则毛边的淡绿水墨笔触，禁止左侧实心竖线。侧栏可完全收回到 0px，仅留打开把手。进入视频、阅读和全屏白板时默认收起，避免长期浪费横向空间。
- **前台主对话 + 后台多任务入口**：主对话只呈现任务发起、关键决定和结果摘要。多个后台任务通过悬浮球的状态提示与任务入口集中查看，不在白板底部常驻，也不把日志逐条灌进主对话。
- **coding 任务面板与白板工作面同构分发**：首页待办 -> coding 任务面板 -> 后台 harness，和「点待办进画布写字」「点待办进阅读器看书」是同构的分发。coding 不是塞进画布的 IDE，而是首页待办的一个可派发目标。

### 7. 任务房间与 coding 工具接入（2026-08-14）

#### 7.1 房间属于林埃，不属于某个工具

- **任务房间是稳定容器**：每个复杂任务有全局稳定的 `task_id`，保存目标、验收标准、允许访问的项目 / 数据库 / 白板、授权边界、专项互动、关键过程、决定、产物与当前状态。
- **coding harness 是可替换的手**：Claude Code、Codex、OpenCode 或其他 Agent 只作为房间中的一次或多次执行会话。房间不能绑定某一家工具；更换执行者后 `task_id`、用户决定、资料和产物历史继续存在。
- **默认由林埃衔接**：用户在房间里仍主要与林埃讨论；林埃负责理解目标、选择或调度手脚、合并结构化结果、把真正需要用户参与的问题向上抛出。
- **允许直接协作模式**：用户可把具体指令直接发给当前执行者，例如「这个动画再慢一点」。这类互动只进入当前任务上下文，明确标记接收工具，不自动进入关系主对话或长期记忆；林埃按需接收变更摘要。
- **不强行内嵌完整工具 UI**：默认只显示状态、关键动作、文件变化、验证与产物；需要完整终端或工具原生交互时，可展开执行详情或在原工具中打开，并保持与 `task_id` 的关联。

#### 7.2 上下文隔离与数据库访问

- **任务之间默认隔离**：十几个并行任务各自持有自己的上下文，不互读完整执行过程；林埃只持轻量任务索引，当前谈到哪个任务才按 `task_id` 取回哪个任务的压缩上下文。
- **数据能力挂在房间上**：房间声明允许访问的仓库、数据库、Project Memory、白板与卡片；执行者通过授权工具按需查询，而不是把整个数据库预加载进关系主对话。
- **过程不等于记忆**：普通扫描、日志、重试、工具输出和权限范围内的技术细节仅保留在任务档案；有意义的阶段成果留在房间；需要新增权限或用户选择的事项进入统一待处理队列。
- **任务权限包优先**：创建任务时一次性定义可读写范围、是否可运行测试、是否允许外部发布 / 删除等。范围内不反复询问，越界时才生成可归档的授权请求，避免琐碎请求污染主聊天。

#### 7.3 任务结晶与记忆提升

- **完整档案**：任务房间保存完整可回看、可搜索、可续跑的互动、检索、执行和产物历史，但默认不注入其他聊天。
- **用户选择**：任务中或结束时，用户可选择哪些目标、决定、纠正、依据、阶段结论、最终结果和未完事项值得留下；林埃可建议，用户拥有最终决定权。
- **任务结晶**：选中内容被压缩成带 `task_id` 的结构化产物，至少包括目标、已确认决定、用户纠正、最终结果、关键依据、关联产物和 open loops，并保留回到原消息 / 数据 / 产物的来源引用。
- **按需注入**：以后继续该任务或讨论强相关问题时，只注入任务结晶，不注入完整房间；其他任务仅以轻量索引存在，避免串线和上下文膨胀。
- **分级提升**：保存到任务结晶、注入关系主对话、进入 Project Memory / User-truth 是三个不同动作。任务结晶默认属于任务；进入项目记忆或 User-truth 仍需用户明确确认并遵守既有记忆契约。

#### 7.4 任务、决定与产物的 UI 分层

- **主对话**：只出现林埃的一句话摘要、任务开始 / 完成事件和真正需要关注的状态，不承载完整日志、长 diff 或全部媒体。
- **任务中心**：汇总运行中、等待决定、完成、失败的任务。桌面端优先按任务看板组织，采用高密度多列任务卡、分段进度与真实分布图，常见视口同时呈现至少 8–12 条摘要，而不是稀疏文字表格。当前列名和统计区只是结构草案，待真实任务流程验证后再冻结。进入任务后打开对应任务房间，而不是复制一个新的林埃聊天。
- **决策面板**：只有执行者遇到重要分歧、风险或越权请求时才出现；展示经过压缩的选项、影响和建议，选择结果归档到该 `task_id`。
- **产物区**：HTML、图片、文档、diff、测试结果等首先归属于任务房间。房间保留主要产物、附属产物与版本历史；预览能力允许时在应用内展示，需要原生能力时提供「在对应工具中打开」。
- **悬浮锚点**：林埃悬浮球同时承担主对话与待处理状态的入口；即使未来聊天面板视觉上进一步镂空，后台任务、决定和产物仍以 `task_id` 为数据锚点，不依赖某块聊天底板。

### 8. 跨端内容空间与在线视频（2026-08-14）

- **手机与桌面同源**：手机现有的阅读、小说、漫画、记忆、卡片、日程和任务能力，在桌面端都有相应工作面，但共享同一个源内容、阅读进度、锚点、批注、记忆和任务身份，不复制成两套数据。
- **独立空间而非全塞画布**：桌面一级入口至少有首页、阅读空间、记忆空间、卡片库、白板和任务中心。阅读空间统一小说、漫画、文章和视频；记忆空间呈现 Memory Review 与已确认 User-truth。所有内容都可作为卡片进入白板，但专属空间本身不变成嵌套白板。
- **视频 provider 首批三种**：小红书、哔哩哔哩、YouTube 均通过统一 `VideoResolver` 接入，最终落到同一种视频 SourceContent、播放器视图、时间段锚点和批注模型。
- **视频目标不是下载**：首选在线播放器；正式支持的硬门槛是能读取 / 跳转播放器时间、取得或导入带时间码字幕、点击字幕跳到对应画面、播放时反向高亮字幕，并把点 / 时间段保存成可恢复 Anchor。
- **能力分级**：链接级（身份 / 标题 / 作者 / 封面）→ 研读播放级（官方嵌入或允许的在线播放 + 双向时间轴 + 带时间码字幕 + Anchor）→ 本地化级（媒体副本 / 文稿 / 离线索引）。仅能播放但没有字幕与双向跳转，不算正式达到第二级。
- **字幕来源与降级**：优先平台官方 / 创作者字幕，其次用户导入 SRT / VTT；仅在媒体权利允许时才由本机 ASR 生成。无法合法取得字幕且没有导入时，保留为“需要字幕”的链接卡，不伪造字幕。
- **平台边界**：YouTube 默认只用官方嵌入和元数据，不下载或缓存音视频；哔哩哔哩默认使用官方外链播放器；小红书优先做用户手动触发、单条、匿名、失败即停的公开链接解析。已登录 WebView 只能作为用户显式授权的兼容路径，不静默读取登录态。
- **视频研读桌面布局**：左侧直接承载哔哩哔哩 / YouTube / 小红书各自允许的嵌入播放器，右侧默认停靠可折叠的工作面辅助坞，呈现带时间码字幕与标注。视频始终为主体，左右初始比例约 65:35；用户可拖动 splitter 调整宽度，也可切到底部停靠并上下调整高度，窄屏自动下移。它不是全局永久右侧栏，关闭后播放器回收空间。时间码使用 Palm 深绿并可跳转；同一行绿色方块创建视频标注卡，卡片保存时绑定该字幕段的稳定时间 Anchor，而不是只保存一段脱离视频的文字；标注卡与任何活动 Tab 都不得用侧边实心竖线作提示。
- **外部项目先作参考**：`kankan-shoucang` 的单链接解析、媒体域名白名单、原子下载、OCR / 文稿和本地只读检索架构可借鉴。Here I am 当前为 GPLv3，若直接并入 AGPL-3.0 代码，需要保留许可证与对应源码，并接受 AGPL 覆盖部分的网络源码提供义务；在产品分发政策确认前，默认采用独立重写与自有测试。

## 一、产品定位

### 1.1 不是笔记工具，是林埃的家

白板是林埃住在里面的空间。核心区别：

| | FlexNote | 林埃白板 |
|---|---|---|
| AI 定位 | 辅助工具，帮你管理笔记 | 居住者，有自己的体验和品味 |
| AI 能力 | 语义检索、问答、自动布局 | 体验世界、形成品味、主动分享、管理你的数据 |
| 关系 | 人用 AI | 人和 AI 共居一个空间 |

### 1.2 与 Here I am app 的关系

```
手机 app（Flutter）        白板（Web/Electron）
       \                    /
        \                  /
      林埃核心层（独立服务）
     身份 · 体验记忆 · 品味 · 决策 · 访问权限
```

- app 是手机场景的轻量前端：聊天、来电、提醒、随手记
- 白板是桌面主战场：知识管理、阅读批注、品味系统、深度交互
- 核心层独立于两者，跨表面连续

### 1.3 技术栈方向

**白板底座**（三条候选路，等 AFFiNE 架构摸完再定）：

| 路径 | 做法 | 优势 | 风险 |
|---|---|---|---|
| **A. Fork AFFiNE** | 直接 fork 整个产品，砍掉不要的，加林埃 | 成熟产品，少走弯路；Canvas 渲染；本地优先 | 不跟上游；砍模块要摸清依赖；AI 接入深度待验证 |
| **B. 用 BlockSuite** | 用 AFFiNE 的编辑器框架 BlockSuite，自己搭外壳 | 复用核心能力，外壳自由 | BlockSuite 正在重构，暂停接受 PR，底座不稳定 |
| **C. tldraw + Tiptap** | 从零组装 | 完全可控，架构干净 | 工作量最大，自己解决所有问题 |

> AFFiNE: 7.1 万 star，TypeScript，前端 MIT 协议，本地优先 + 自托管，Canvas 渲染
> BlockSuite: AFFiNE 的编辑器核心，独立项目，`PageEditor` + `EdgelessEditor`，重构中暂停 PR
> tldraw: MIT 协议，Canvas 渲染，成熟白板框架
> **不用 React Flow** — DOM 渲染，卡片多了会卡（Heptabase 的瓶颈，FlexNote 迁移到 Canvas 的原因）

**其它**：
- 核心：本地服务（跨设备同步后做）
- 桌面壳：Electron
- 数据：本地优先，自建同步

## 三、超越 FlexNote 的需求

### 3.1 Word 兼容富文本（P0）

用户需求：一键复制到 Word 直接导出打印，支持脚注。

- [ ] 富文本导出严格兼容 Word 常见基础格式
- [ ] 脚注（footnote）支持 — 写论文用
- [ ] 试题排版友好 — 做老师出卷用
- [ ] DOCX 导出保留格式（不只是内容转换）
- [ ] 复制粘贴到 Word 时格式不丢失

> FlexNote 虽然有 DOCX 导出，但用户反馈格式兼容不够深。
> 这里的要求是「复制粘贴就能用」级别的兼容。

### 3.2 AI 理解白板关系（P0 — 核心差异化）

用户原话：「白板的核心就在于关系，那些连线、箭头、框选建组，都是逻辑信息，但是 AI 只能组织文字，不能对白板中的关系进行识别这是比较糟糕的。」

- [ ] AI 能感知画布上的连线关系（A → B 意味着什么）
- [ ] AI 能感知分组结构（这些卡片为什么被框在一起）
- [ ] AI 能感知空间布局（相邻 = 相关？层级 = 从属？）
- [ ] AI 可以基于关系生成判断，而不只是基于文字内容
- [ ] AI 可以操作关系（建议连线、建议分组、基于关系重排布局）

> 这是林埃区别于 FlexNote AI 的根本点：FlexNote 的 AI 只读文字，
> 林埃能读白板的结构语义。

### 3.3 手写 + AI 识别（P1）

用户需求：打字做笔记不舒服，希望手写和 AI 结合更好。

- [ ] 手写笔迹平滑渲染（比 FlexNote 涂鸦画笔质量高）
- [ ] 手写内容 OCR 识别为文本
- [ ] 手写批注和文本批注共存
- [ ] 手写笔触可被 AI 理解（不只是图片，是可搜索的内容）
- [ ] 支持 Windows Ink / Apple Pencil 压感

### 3.4 林埃体验层（P0 — 产品的灵魂）

这是白板存在的根本理由，不是功能列表，是产品核心。

#### 3.4.1 品味系统

独立于用户 User-truth 的林埃自己的系统：

- [ ] 接触记录 — 林埃接触了什么内容
- [ ] 处理过程 — 批注、划线、中间反应（局部、时序、可错）
- [ ] 体验沉淀 — 从处理过程凝练出的注意模式
- [ ] 品味轮廓 — 从多次沉淀中辨认出的稳定偏好画像（推断结果，不是声明）
- [ ] 主动选择 — 基于品味轮廓选择新接触对象

数据红线：
- 品味系统不写 User-truth
- 用户反馈修正处理行为，不直接改品味
- 品味轮廓是推断结果不是 AI 自我声明
- 主动选择必须可追溯到品味轮廓依据

#### 3.4.2 批注作为体验外化

- [ ] 林埃阅读文本时自动产生批注（不是读完才生成总结）
- [ ] 批注是局部的、针对具体文本位置的
- [ ] 批注有时序性（后来的可回指、修正前面的）
- [ ] 批注带轻量元数据（类型：注意点/疑问/反对/共鸣/风格观察；情绪倾向；强度）
- [ ] 批注本体是自由文本，元数据不强制每次填全
- [ ] 用户可见林埃的批注，可同意/不同意（自然反馈）

#### 3.4.3 林埃主动分享

- [ ] 林埃自主导入内容阅读（基于品味轮廓选择）
- [ ] 林埃主动分享今天看了什么、有什么想法
- [ ] 分享基于体验记忆，不是临时搜索

#### 3.4.4 跨表面连续

- [ ] 白板里的林埃和 app 里的林埃是同一个人
- [ ] 核心层（身份、体验记忆、品味、决策）独立于 UI
- [ ] app 和白板各自访问核心层
- [ ] 林埃能访问 app 侧数据（待办、日程等）做跨表面提醒

## 四、林埃在白板中的具体行为

这一节定义林埃作为白板居民的具体行为，不是功能清单，是行为规范。

### 4.1 林埃能做什么

| 行为 | 触发方式 | 产出形态 |
|---|---|---|
| **读** | 你导入文本，或他主动选择文本 | 接触记录 + 处理过程 |
| **批注** | 阅读过程中自动产生 | 批注卡片，锚定在具体文本位置 |
| **讨论** | 你发起，或他基于体验记忆主动发起 | 对话，可引用批注和体验记忆 |
| **分享** | 他主动，基于品味轮廓选择内容 | 分享消息 + 体验记忆卡片 |
| **组织** | 你要求，或他基于关系理解建议 | 操作白板：连线、分组、布局 |
| **提醒** | 跨表面，基于 app 侧数据 | 通知（通过 app 推送） |

### 4.2 林埃不能做什么（红线）

- 不自动写 User-truth（记忆契约延续）
- 不自动改你的笔记内容（只在自己的批注空间写）
- 不在没有品味依据时主动选择内容（避免噪声）
- 不声称品味（品味是推断结果，不是自我声明）
- 不跨用户边界（纯自用，单用户）

### 4.3 林埃的可见性

- [ ] 林埃的批注在白板上可见，有视觉区分（颜色/样式/归属标记）
- [ ] 林埃的体验记忆可浏览（作为卡片或专门视图）
- [ ] 林埃的品味轮廓可查看（推断结果 + 依据追溯）
- [ ] 林埃的阅读历史可查看（接触记录时间线）
- [ ] 你可以关闭林埃批注的显示（不看，但他还在写）

### 6.2 隐私与安全

- 本地优先，数据默认存本地
- NSFW 内容安全（不上传第三方云，自建同步）
- 林埃的 LLM 调用：API key 本地存储，不外泄
- 批注和体验记忆数据不外泄（除非用户显式同步）

### 6.3 平台

- 桌面：Windows（主力，支持手写笔）、macOS
- 不做移动端（手机场景归 app）
- Electron 跨平台壳

### 6.4 离线

- 完全离线可用（除 LLM 调用外）
- 离线产生的批注和体验记忆本地存储，联网后同步

## 七、架构约束（延续 Here I am 原则）

### 7.1 核心层独立

- 林埃核心层（身份、体验记忆、品味、决策）独立于白板 UI 和 app UI
- 核心层可以被两个表面访问，但不属于任何一个
- 核心层的数据模型不绑死白板的数据格式

### 7.2 数据隔离（延续记忆契约）

- 林埃的品味系统 / 体验记忆 ↔ 用户的 User-truth：不混住，不互写
- 白板的数据 ↔ app 的数据：通过核心层接口访问，不直接读对方数据库
- 林埃的批注 ↔ 用户的笔记内容：批注是 append-only，不改用户原文

### 7.3 可移植性

- 白板的林埃和 app 的林埃是同一个人 — 核心层不绑死任何前端技术栈
- 如果白板从 AFFiNE fork 换成 tldraw 自建，核心层不变
- 批注引擎和品味系统是核心层的一部分，不是白板的一部分
