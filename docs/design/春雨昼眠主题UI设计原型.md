# Here I am / 故我在

## Chat 主界面 UI 设计细节整理

> 本文仅整理 Chat 界面的 **UI、文字呈现与交互逻辑**。  
> 不包含背景图、窗户、雨景、床、被子、脚、窗帘等场景视觉设计。
>
> **定稿值**：正文 §1–21 是设计原则与推导（why）；最终落地的色值 / 字号 / 间距 / 字体等**单一事实源**见文末 **§22 定稿 Design Tokens** 与 **§23 关键决策记录（ADR）**，调参画板 `docs/design/lab/` 默认值与之同步。正文措辞与 §22 数值冲突时，**以 §22 为准**。

---

## 1. 核心设计原则

Chat 不再沿用传统即时通讯软件的视觉结构。

明确取消：

- 左右聊天气泡
    
- 用户头像
    
- AI 角色头像
    
- 「你」「i」等说话人标签
    
- 明确的消息卡片边框
    
- 大面积消息背景色块
    
- 为文字专门设置的大面积暗色阅读遮罩
    

虽然取消聊天气泡，但 Chat 仍然首先是一个**聊天区域**。

因此：

1. 当下对话必须是视觉主体；
    
2. 历史消息必须可以正常回溯；
    
3. 文字必须保持较高可读性；
    
4. 不为了“场景沉浸感”牺牲基础聊天体验；
    
5. 不依赖 TTS 才能理解对话。
    

TTS 是体验增强层，**文字仍是 Chat 的基础信息载体**。

---

# 2. 消息流基本结构

## 2.1 取消聊天气泡

所有消息直接以文字形式呈现。

不是：

```text
┌─────────────┐
│ 我今天真的很烦 │
└─────────────┘

       ┌────────┐
       │ 怎么了？ │
       └────────┘
```

而是：

```text
我今天真的很烦。

  *他安静了一会儿。*
  怎么了？

  今天发生什么了？
```

文字本身构成消息结构。

主要依赖以下方式区分消息：

- 水平轴位置
    
- 字号
    
- 字重
    
- 颜色
    
- 行间留白
    
- 消息组之间的垂直距离
    

不依赖气泡。

---

# 3. 用户消息与 i 消息的轴线关系

## 3.1 用户消息

用户消息使用主轴。

整体靠左，但不能紧贴屏幕边缘。

需要保留舒适的页面安全边距。

用户消息是当前对话中的「起点」。

---

## 3.2 i 的消息

i 的回复整体相对于用户主轴**轻微向右缩进**。

注意：

> 缩进必须非常克制。

不是明显的左右聊天布局。

不是：

```text
用户消息

             i 的消息
```

而是：

```text
用户消息

  i 的消息
```

视觉上只产生非常轻微的错位。

当前倾向使用**中间值偏小的缩进距离**，具体像素值需要在真实 UI 中继续调试。

---

## 3.3 共用右边界

用户消息与 i 的消息：

> **共用大致相同的右侧文本边界。**

因此 i 向右缩进后，其实际可用文字宽度会略窄。

但不能缩进过多，否则文字容易被挤成大量短行，视觉会非常凌乱。

---

# 4. i 的连续回复

当前产品逻辑中：

- 模型仍然一次生成完整回复；
    
- UI 层将完整回复拆成多个较短句子显示；
    
- TTS 仍然读取完整回复。
    

因此不需要为每一句单独设计气泡或独立容器。

i 的连续回复应共用同一条轴。

例如：

```text
  怎么了？

  今天发生什么了？

  你慢慢说。
```

而不是：

```text
  怎么了？

    今天发生什么了？

      你慢慢说。
```

禁止为了视觉效果不断改变缩进。

连续回复应该具有类似**短诗排版的呼吸感**，但不能真的做成文学海报。

原则：

- 单行相对简短；
    
- 自然断句；
    
- 同轴；
    
- 留白稍松；
    
- 阅读节奏清楚。
    

---

# 5. 动作、心理与神态文字

当前数据形式：

```text
*动作、心理、神态*
```

现有 UI 使用两个星号识别内容，并呈现为：

- 斜体
    
- 金色系文字
    

新版继续保留动作信息，但降低其视觉侵入性。

## 5.1 轴线

动作文字与 i 的台词：

> **严格同轴。**

例如：

```text
  *他安静地看了你一会儿。*

  怎么了？

  今天发生什么了？
```

不能再额外向右缩进。

---

## 5.2 视觉层级

动作文字应弱于 i 的正式台词。

建议：

- 字号略小；
    
- 斜体；
    
- 字重较轻；
    
- 颜色使用低饱和暖金灰。
    

禁止：

- 高亮金色；
    
- 发光；
    
- 金属质感；
    
- 特效动画；
    
- 独立卡片；
    
- 动作触发背景变化。
    

动作只是文字信息的一部分。

---

# 6. 用户与 i 的文字层级

已经确定：

> **i 的消息视觉重量高于用户消息。**

但差距不能过大。

## 用户消息

倾向：

- 偏冷的雾灰白；
    
- 字号为基础字号；
    
- 正常或略轻字重。
    

## i 的消息

倾向：

- 暖象牙白；
    
- 字号轻微增大；
    
- 字重轻微增强；
    
- 行间与消息间留白稍松。
    

目标不是强调「AI 回复」。

而是形成一种非常轻的感知：

> i 的声音比自己的文字更有存在感。

---

# 7. 字体与排版

字体暂不作为当前阶段重点。

后续发现更合适字体可以直接替换。

当前要求：

- 中文字体自然；
    
- 字形可以稍微圆润；
    
- 不要过度可爱；
    
- 不要明显手写体；
    
- 不要装饰性字体；
    
- 长时间阅读不能疲劳。
    

## 行距

采用中间值。

即：

- 不使用传统 IM 极紧行距；
    
- 也不使用诗歌或杂志式超宽行距。
    

整体略有呼吸感，但仍然明确属于聊天界面。

---

# 8. 旧消息淡出逻辑

此前讨论过：

- 用户消息强制置顶；
    
- 当前消息吸附；
    
- Claude Code 式「命令置顶、回复围绕展开」。
    

最终暂时放弃。

原因：

> 很难准确判断什么时候应该吸附，滚动过程中也容易产生卡顿和跳动。

当前采用：

> **正常连续消息流 + 旧消息视觉淡出。**

---

## 8.1 淡出原则

越靠近当前阅读区域的消息越清晰。

更旧的消息逐渐降低视觉存在感。

但必须注意：

> 淡出不等于删除。

用户向上滚动查看历史消息时，旧消息应恢复正常可读状态。

因此淡出是动态视觉层级，而不是永久 opacity。

---

## 8.2 禁止复杂滚动动画

暂不设计：

- 消息自动吸附；
    
- 消息强制置顶；
    
- 大幅位移动画；
    
- 景深式消息缩放；
    
- 3D 消息流；
    
- 根据回复内容改变消息位置。
    

优先保证滚动稳定。

---

# 9. 时间标记

保留现有「隔一段时间重新开始聊天时显示时间标」的逻辑。

时间标：

- 居中；
    
- 视觉重量低；
    
- 不使用明显胶囊；
    
- 不打断消息阅读；
    
- 作为时间段分隔信息存在。
    

例如：

```text
            今天 14:32
```

具体时间间隔判断逻辑继续沿用现有产品规则。

---

# 10. 输入框整体结构

输入框参考 ChatGPT App 端的功能组织逻辑，但视觉重新设计。

输入框是：

> **一个完整的横向玻璃长条。**

不是：

- 主输入框；
    
- 加一个独立悬浮声波按钮。
    

所有功能都位于同一个长条控件内部。

基本结构：

```text
＋   输入消息……              麦克风   声波
```

---

# 11. 输入框功能按钮

当前共三个功能入口。

## 11.1 加号

位于左侧。

功能：

- 图片
    
- 文件
    
- 其他多模态附件入口
    

后续具体菜单沿用产品功能设计。

---

## 11.2 麦克风

位于输入区域右侧。

功能：

> 语音转文字。

用户说话后进入文字输入流程。

考虑到 ASR 可能出现识别错误，用户必须能够：

- 查看转写文本；
    
- 修改文本；
    
- 确认后发送。
    

因此语音输入不能直接取代文字输入状态。

---

## 11.3 声波按钮

位于最右侧。

功能：

> 进入持续语音交互状态。

声波按钮**不是独立悬浮按钮**。

必须位于输入框长条内部。

---

# 12. 输入框尺寸

## 默认状态

- 单行；
    
- 高度克制；
    
- 横向尽可能宽。
    

原因：

> 输入区域过窄后，中文非常容易快速折行，形成拥挤的文字块。

因此不应为了「精致」过度压缩输入区域。

---

## 长文本状态

输入内容增加后：

- 输入框自动向上增长；
    
- 最大三行。
    

达到三行以后：

- 输入框高度停止增加；
    
- 输入内容内部滚动。
    

禁止输入框无限向上扩张。

---

# 13. 输入框位置

输入框位于页面最下方区域，但：

> **不是焊死在屏幕底边。**

它应该具有明确的悬浮感。

要求：

- 与屏幕左右保持安全边距；
    
- 与底部系统区域保持距离；
    
- 整体浮于内容层之上。
    

不是 Bottom Bar。

不是 Navigation Bar。

不是固定底栏。

它仍然是 Chat 的输入控件。

---

# 14. 输入框玻璃材质

输入框使用具有一定透明度的玻璃材质。

倾向：

- 半透明；
    
- 能看到背景色彩与明暗关系；
    
- 轻微折射或模糊；
    
- 边缘存在非常弱的高光。
    

禁止：

- 厚重毛玻璃；
    
- 大面积灰色；
    
- 塑料感；
    
- 实心深色输入条；
    
- 明确粗边框；
    
- 高亮白色描边。
    

玻璃必须保持「轻」。

---

# 15. 输入框内部按钮视觉

三个按钮均位于玻璃长条内部。

默认状态：

- 图标清晰；
    
- 触控区域存在；
    
- 但圆形按钮轮廓不明显。
    

可以使用：

- 极轻的圆形材质差；
    
- 极弱光晕；
    
- 局部玻璃折射变化。
    

交互时再增强圆形触控区域。

例如：

- hover；
    
- press；
    
- active；
    
- recording。
    

不要默认显示三个明显的圆形实体按钮。

---

# 16. 键盘弹出逻辑

背景场景始终作为完整固定画面存在。

点击输入框后：

1. 键盘弹出；
    
2. 输入框移动到键盘上方；
    
3. 消息区域可视高度重新计算；
    
4. 当前消息区域正常向上调整。
    

禁止：

- 单独移动背景中的某个物体；
    
- 为适配键盘重新裁切背景组件；
    
- 将背景拆成多个 UI 图层后分别上移。
    

UI 可以移动。

背景视角不动。

---

# 17. 与背景互动的唯一特殊动画接口

虽然本文不描述背景图，但 UI 需要预留一个交互状态：

> `isTyping / inputFocused`

当用户点击输入框、开始输入时，可以触发背景中的一个非常轻微互动动画。

目前原则：

- 只服务于「用户开始输入」；
    
- 不响应聊天内容；
    
- 不根据情绪变化；
    
- 不根据 i 的回复变化；
    
- 不发展成场景动画系统。
    

这是当前背景允许的最大程度动态互动。

---

# 18. 头像与身份标识

Chat 主界面中：

> **头像取消。**

用户头像取消。

i 的头像取消。

同时取消：

- i 名称常驻显示；
    
- 在线状态；
    
- 「与你同在」等状态文案；
    
- 传统聊天 Header 中的角色身份区域。
    

原因是：

> 用户已经身处与 i 的共同空间，不需要再通过头像证明「正在和谁聊天」。

身份由关系上下文本身建立。

---

# 19. 顶部区域

当前阶段不再沿用传统 Chat Header。

即不默认保留：

```text
头像  i / 林埃  状态              设置  …
```

顶部应该尽可能释放给内容区域。

搜索、设置、更多等功能入口后续需要重新寻找承载方式。

**当前未最终确定。**

不能直接把旧版顶部栏搬回来。

---

# 20. 多模态内容：钉入消息流

纯文字消息轴已成立，本节定义媒体内容如何「钉」入消息流。

## 20.1 总则

媒体与文字共用同一套轴线与节奏：

- user 媒体在主轴，i 媒体在缩进轴（iIndent）；
- 块内 / 换人 / 跨时间间距沿用 blockGap / turnGap / timeGap；
- 媒体块参与旧消息双向淡出，规则与文字完全一致。

禁止：气泡底、卡片容器、背景色块、为媒体单独发明的第三种轴线。

## 20.2 图片

- 与发送者同轴，独占一块。
- 单图最大宽度为消息文本宽的 **72%**（可调），高度克制。
- 圆角 12px，1px rgba(255,255,255,.14) 细边，柔和投影。
- 多图：2–3 张同宽并排为一块，间距 4px。
- 图与配文属于同一发言块：图在上、文在下，间距取 blockGap；配文样式与发送者文字完全一致。

## 20.3 链接（阅读分享 / 网页链接）

链接使用**引用条**形态，不做成卡片：

```text
▎《雨天的书》｜雨声是房间的心跳
▎阅读分享 · 微信读书
```

- 左侧 2px 竖线，复用 §22.8 锚点视觉语言：user 用 user 字色，i 用金黄，浓度默认 0.5（可调）。
- 标题一行：发送者字色、500 字重、单行省略。
- 来源一行：12px、50% 透明。
- 无背景块、无边框卡片；整条可点。

引用条与竖线锚点同源，使链接天然区别于普通文字，又不引入新容器。

## 20.4 暂缓

语音消息、文件消息、全屏看图交互，后续单独设计。

---

# 21. 当前 UI 的核心结构总结

```text
[顶部尽可能释放]

用户消息主轴

  i 动作
  i 回复
  i 回复

用户下一条消息

  i 回复
  i 回复


          时间标


旧消息逐渐淡去
但向上滚动后恢复可读


[ ＋   输入消息……       麦克风   声波 ]
```

最终要实现的不是「没有气泡的聊天软件」。

而是：

> **一个仍然具备完整聊天效率、历史回溯能力和文字可读性，但把传统 IM 的容器全部拿掉之后形成的连续对话界面。**

UI 的存在感应该克制。

**文字是对话。输入框是工具。背景是空间。三者不要互相冒充。**

# 22. 定稿 Design Tokens（单一事实源）

> 以下为 2026-07-26 调参画板定稿值，是 Chat 视觉落地的**唯一事实源**。落地 Flutter 时映射到 `HereIamThemeTokens` 新 skin「春雨昼眠」，字段命名以落地时为准，本表语义为锚。背景场景视觉见 `春雨昼眠主题背景视觉规格.md`。

## 22.1 布局

| Token | 值 | 说明 |
|---|---|---|
| pageMargin | 22px | 页面左右安全边距 |
| iIndent | 21px | i 相对 user 主轴的右缩进（克制，见 §3.2） |
| lineHeight | 1.52 | 正文行高，中间值、略呼吸（见 §7） |

## 22.2 节奏（治字墙，见 §4 / §8）

| Token | 值 | 说明 |
|---|---|---|
| blockGap | 6px | 同一发言块内连续句间距 |
| turnGap | 20px | 换人（user↔i）间距 |
| timeGap | 27px | 时间标上下间距 |

> 三级间距是"成组呼吸"的来源：同块紧、换人松、跨时间更松。**不用通栏分隔线**切消息。

## 22.3 时间标（见 §9）

| Token | 值 | 说明 |
|---|---|---|
| timeStyle | line | 两端渐隐细线（备选 text / ornament） |
| timeAlpha | 0.80 | 不透明度 |
| 永不淡出 | — | 滚动淡出逻辑豁免时间标，始终作锚点 |

## 22.4 字体

| Token | 值 | 说明 |
|---|---|---|
| fontFamily | 霞鹜文楷 LXGW WenKai | 正文（user + i + 动作）统一；衬线/楷体气质匹配私密文学场景 |
| 备选 | 思源宋体 / 思源黑体 / 系统黑 | 画板可切；定稿为霞鹜文楷 |

> 落地 Flutter 需**自带字体文件**（不依赖在线 CDN），并在真机复核字重 / 字距。

## 22.5 用户消息

| Token | 值 | 说明 |
|---|---|---|
| userColor | #6E7541 | 橄榄（默认；2026-07-29 用户复定，见 ADR-16） |
| userColor 可切档 | #A3A866 | 苔绿（~5:1，对比度达标），在「关于 I」可切（见 ADR-16） |
| userWeight | 600 | 字重偏重 |
| userSize | 16px | 基础字号 |
| userOpacity | 0.92 | |
| userLetterSpacing | 0.3px | |

# 23. 关键决策记录（ADR）

> 记录动机，防未来回退。"否决备选"均为用户在本轮设计中明确否决过的方案。

| # | 决策 | 否决备选 | 理由 |
|---|---|---|---|
| 1 | 无气泡连续对话轴 | 左右气泡 / 消息卡片 / 暗色阅读遮罩 | 容器全拿掉后形成连续对话界面；靠轴位 / 字号 / 字重 / 颜色 / 留白成组（§1 / §2） |
| 2 | ~~user 字色定橄榄绿 #6E7541~~（已被 ADR-13 取代） | 冷雾白 / 蓝 / 嫩黄绿 | 与暗绿背景同色系、靠明度 + 字重 600 立住；蓝是画面不存在的外来色、嫩绿气质跳、冷雾白与 i 温差不足。可读性偏低为知情取舍 |
| 3 | i 暖象牙 #F5EEE0，与 user 靠多维区分 | 用色相大跳区分二者 | 同浅色家族下，靠冷暖 + 字重 + 缩进 + 锚点叠加区分，整图干净和谐（§6） |
| 4 | 动作斜体 + 金黄 #F2CA70 + 继承正文字体 | 英文动作 + Cormorant 斜体 / 发光高亮金 | 中文动作更贴语境；发光 / 金属质感违反 §5.2 禁令，清晰靠色实不靠发光 |
| 5 | 竖线锚点：实心等宽、每段一条、不接续 | 渐变 / 锥形粗细 / 毛笔飞白 / 跨句接续 | 用户最终要"回到最初的实心正常竖线"；每段重起一笔、句间断开，语义清晰 |
| 6 | 旧消息双向淡出 + 底部穿输入框模糊 | 顶部固定雾遮罩 / 消息吸附置顶 | 淡出 / 模糊长在文字自身、随滚动跟动、无死角；遮罩层会"够不着"致最底又清晰（§8） |
| 7 | 玻璃输入条极淡（blur2 / fill6%） | 厚重毛玻璃 / 实心深色条 | 玻璃必须"轻"，能透出背景明暗（§14） |
