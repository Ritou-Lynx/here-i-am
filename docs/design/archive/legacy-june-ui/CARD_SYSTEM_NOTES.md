# Here I Am Card System Notes

本文档记录新 UI 下的卡片系统问题。它不是 Flutter 实现方案，而是为后续重新设计“从对话抽取记忆生成卡片”提供方向。

## 背景

现有代码里已经有一套较丰富的卡片模板系统，主要集中在：

- `lib/ui/core/cards/native_card_factory.dart`
- `lib/ui/core/cards/templates/`
- `lib/ui/core/cards/native_widget_factory.dart`

这些模板覆盖文本、视觉、量化、时间、实体、洞察等类型。它们更像旧 Memex timeline / insight / card agent 的通用卡片系统。

现在新增的“从对话中抽取记忆生成卡片”不是简单再套旧模板。它承担的是伴侣产品里的长期生活记忆，需要统一世界观，同时保留内容形态变化。

## 当前问题

- 新抽取记忆卡片外观过于统一，缺少内容类型差异。
- 旧模板风格与 Here I Am 的水汽、凝露、玻璃、气泡语言不一致。
- 旧 timeline 长列表将被移出主路径，卡片不应继续围绕“无限 timeline”设计。
- Memory Review 里的卡片和长期记忆详情卡不是同一个尺寸和任务。

## 新卡片的两种层级

### 1. Memory Summary Card

位置：
- Memory Review 圆柱屏。
- 记忆云/星云里点开水珠后出现。

职责：
- 展示 AI 整合后的记忆摘要。
- 让用户快速判断这条记忆是什么。
- 提供进入对话修正和全屏详情的入口。

形态：
- 同一张卡，不区分 review mode / dew mode。
- 在圆柱屏里就是瀑布流中的摘要卡。
- 在记忆云里就是水珠展开后的摘要卡。
- 外层位置、转场、背景可以不同，但卡片本体的信息结构一致。

### 2. Full Detail View

位置：点击 Memory Summary Card 整体后进入。

职责：
- 展示完整记忆信息。
- 展示全部来源证据、结构化字段、修订历史、相关内容。
- 承担审计和深度修正前的查看。

形态：
- 可以全屏。
- 信息密度最高。
- 视觉可以延续凝露语言，但阅读效率优先。

## 每张记忆卡必须具备的信息板块

先定信息结构，再定视觉。下面是新记忆卡片的最低信息骨架，Memory Summary Card 和 Full Detail View 都从这套骨架裁剪。

### A. 记忆主体

必须回答：这条记忆是什么。

字段：
- 水珠短标识：2-4 个字，服务于气泡/水珠中的快速识别，不一定出现在卡片正文里。
- 摘要：1-3 句，说明发生了什么或记住了什么。
- 类型：event / task / plan / schedule / fact / emotion 等。
- 当前状态：待确认、已确认、已修改、已撤销、已完成、已取消。

Memory Summary Card 中：
- 摘要必须首屏可见。
- 水珠短标识可以作为角标/弱标识，也可以不显示。
- 类型可以轻量显示。
- 默认不需要再放一个大标题，避免和摘要/事件总结重复。
- 状态变化不在这一级完整展开。

Full Detail View 中：
- 摘要、来源证据、结构化字段和状态变化都应可读。

设计结论：
- “标题”这个词在新记忆卡里容易造成混淆，后续应拆成 `dropletLabel` 和 `memorySummary`。
- `dropletLabel` 只面向水珠上的 2-4 字短文案，不属于标签体系，也不进入卡片 Foot。
- `memorySummary` 面向 Review Card、Dew Card 和 Full Detail View，是卡片主体内容。
- 如果底层暂时仍需要 `title` 字段，优先把它理解为兼容字段，不作为卡片必须展示的大标题。

### B. 来源与证据

必须回答：这条记忆从哪里来，为什么可信。

字段：
- 来源：来自哪段对话 / 哪次捕获 / 哪个外部数据流。
- 时间：生成时间，以及原始事件时间。
- 角色/参与者：用户、角色、其他人。
- 原文摘录：展示用户原话或原始记录片段。
- 置信度或待确认原因：可选，但对审核很有价值。

Memory Summary Card 中：
- 显示来源入口或来源数量。
- 不强行显示一个唯一时间/地点，因为整合记忆可能来自多条聊天记录。

Full Detail View 中：
- 可以展开查看原始对话片段或来源详情。
- 每条来源可携带自己的时间和地点参数。

### C. 用户可操作区

必须回答：用户现在能怎么处理它。

Memory Summary Card 必须有：
- 问问 TA / 讨论修正：和角色沟通哪里总结错了、应该怎么改。
- 进入详情：点击卡片整体进入 Full Detail View。

Full Detail View 可以有：
- 问问 TA。
- 手动编辑摘要。
- 查看全部来源。
- 查看修订历史。
- 在云中定位。
- 关联日程 / 任务 / 人物 / 作品等后续动作。

设计结论：
- 不把“删 / 改 / 撤”做成 Review Card 上的三个主要按钮。
- 一张记忆卡可能由多条聊天记录、多次追加、多次修正整合而来，单一撤销按钮无法清楚表达影响范围。
- 主要修正方式应该是“和 AI 对话修正”，让角色理解用户要改哪里，并同步处理相关字段、关联记录和后续影响。
- 手动编辑只用于局部调整 AI 摘要；编辑后需要触发 AI/系统重新检查相关结构化字段和关联内容。

## 手动编辑边界

手动编辑不能直接等同于“改整条底层记忆”。一条整合记忆可能关联多条来源、结构化字段、相关实体和后续计划，直接让用户改任意字段会牵一发而动全身。

第一版建议：
- 手动编辑只编辑用户可见的 `memorySummary`。
- 不直接编辑 `sourceExcerpts`，来源是证据，不能被改写。
- 不直接编辑 `operationHistory`，历史只能追加新 operation。
- 不在摘要编辑框里直接改关联记忆、日程、任务、人物等隐性结构。
- 用户只需要把正确版本写出来，不需要判断这会影响哪些底层结构。

保存后流程：
1. 先保存一条 `correct` 或 `update` operation，记录用户改过摘要。
2. 标记该记忆为“需要结构复核”。
3. 由 AI/系统根据新摘要和原始来源重新检查结构化字段、tags、归属屏、相关实体。
4. 如果只是表达调整或低风险字段同步，后台自动完成。
5. 如果影响到其他记忆、日程、任务、地点、标签或关联实体，弹出确认提示，让用户同意后再应用。

交互上：
- 小改动走“编辑摘要”。
- 涉及事实变化、时间地点变化、任务状态变化、关联对象变化时，引导用户使用“问问 TA”。
- 编辑界面应提示：相关记忆和字段会在保存后自动复核；需要你同意的改动会再确认。

确认提示原则：
- 只在有跨卡片、跨日程、跨标签、跨实体影响时打扰用户。
- 弹窗文案要说明“将要一起改什么”，不要只说“检测到影响”。
- 用户可以选择：应用全部、只保存摘要、回到问问 TA。

### D. 结构化字段

必须回答：系统如何理解它。

字段按类型变化：
- Event：时间、地点、人物。
- Task：截止时间、完成状态、下一步。
- Plan / Schedule：开始时间、结束时间、提醒、地点。
- Fact：事实对象、属性、稳定性。
- Emotion：情绪词、强度、触发语境。
- Media / Reading：作品名、人物、平台、摘录。
- Health / Body：指标、数值、日期、趋势。

Memory Summary Card 中：
- 只显示最关键 1-2 个字段。

Full Detail View 中：
- 可以完整显示结构化字段。

### E. 关系与归属

必须回答：它应该沉到哪里。

字段：
- 归属屏：Memory Review / Schedule / Health / Interests 等。
- 相关实体：人、地点、作品、设备、账目等。
- 相关记忆：与哪些旧记录有关。
- 情绪坐标候选：后续进入记忆云时使用，第一版先作为视觉投影，不强绑数据。

Memory Summary Card 中：
- 可以显示轻量归属标签。

Full Detail View 中：
- 可以显示相关内容列表。

### F. 修订历史

必须回答：这条记忆有没有被改过。

字段：
- 创建操作。
- 修改操作。
- 撤销操作。
- 完成 / 取消 / 纠正操作。

Memory Summary Card 中：
- 通常不显示，除非刚刚修改或撤销。

Full Detail View 中：
- 应有“历史/来源”入口。

## 信息优先级

Memory Summary Card 优先级：

1. 摘要。
2. 来源入口 / 来源数量。
3. Tags。
4. 问问 TA。
5. 水珠短标识。

Full Detail View 优先级：

1. 记忆摘要。
2. 来源与原文。
3. 结构化字段。
4. 操作区。
5. 相关记忆。
6. 修订历史。
7. 水珠短标识。

## 卡片本体：整合记忆 vs 原始记录

这是新旧系统的核心差异。

旧 timeline card 更接近“原始记录卡”：
- 用户写了什么、拍了什么、记录了什么，卡片忠实保存。
- AI 可以补摘要、标签、日期、地点，但卡片主体仍是原始记录。

SharedLife / 对话抽取记忆更接近“整合记忆卡”：
- 同一件事可能被多次提到、追加、修正、完成或取消。
- 卡片展示的是当前被理解后的记忆状态。
- 原始对话不是消失，而是作为证据和来源挂在卡片后面。
- 卡片边界由语义实体决定，不由聊天输入条数决定。
- 一条很长的用户输入可以拆成多张记忆卡；多条分散的用户输入也可以汇成同一张记忆卡。

设计结论：
- 新记忆卡主路径采用“整合记忆卡”，不是每条原始聊天都生成一张长期卡。
- 原始记录必须保留为证据，不应被 AI 总结替代。
- Memory Summary Card 展示的是 AI 提出的记忆摘要，用户要能进入详情对照原文确认。
- Full Detail View 展示的是“当前记忆 + 来源证据 + 修订历史”。
- 默认卡面主要信息是 `memorySummary`。
- `sourceExcerpts` 和 `operationHistory` 是次级入口，可以通过展开按钮、来源按钮，或点击卡片进入全屏详情查看。

因此不要使用含混的 `body/details` 作为核心概念。建议改成：

| 字段概念 | 含义 | UI 位置 |
|---|---|---|
| `dropletLabel` | 2-4 字短标识 | 水珠；不进入卡片 Foot |
| `memorySummary` | AI 生成、用户可改的记忆摘要 | Memory Summary Card / Full Detail View 主体 |
| `sourceExcerpts` | 用户原文或原始记录片段 | 详情里的证据区 |
| `structuredFields` | 时间、地点、人物、状态、数值等 | 类型化信息区 |
| `operationHistory` | 创建、追加、修改、撤销等事件 | 详情里的历史区 |
| `sourceMetadata.time` | 每条来源记录自己的时间 | 来源区 |
| `sourceMetadata.place` / `location` | 每条来源记录自己的地点 | 来源区；沿用旧卡片系统已有地点能力 |
| `derivedTime` / `derivedPlace` | AI 或系统从多来源中推导出的代表性时间/地点 | 可选结构化字段，低置信时不显示在摘要卡 |

视觉上可以让 `memorySummary` 成为卡片正文，但必须让 `sourceExcerpts` 足够容易打开。否则用户会感觉 AI 在替自己改写人生。

## 卡片查看层级

第一层：Memory Summary Card。
- 展示 AI 总结后的 `memorySummary`。
- 显示来源入口/来源数量、tags、问问 TA。
- 点击卡片整体进入全屏详情。
- 在 Memory Review 圆柱屏里用于看最近 1-2 天新生成的记忆。
- 在记忆云/星云里作为水珠展开后的卡片。

第二层：Full Detail View / 全屏详情。
- 点击 Memory Summary Card 后进入。
- 展示完整记忆摘要。
- 展示全部原始对话来源。
- 展示结构化字段。
- 展示修订历史。
- 展示关联记忆/关联实体。
- 提供编辑按钮。

第三层：对话修正。
- 从卡片进入与角色的对话。
- 用户用自然语言说明哪里错了。
- AI 应同时修正摘要、结构化字段、关联关系，以及必要时追加新的 operation。

## 地点信息

地点信息应保留，并沿用旧卡片系统已有的自动地点能力。

规则：
- 有明确地点时，优先作为来源记录的 `sourceMetadata.place` 或 `sourceMetadata.location`。
- 自动地点只能作为候选或低置信字段，避免凭空推断。
- 对于多来源整合记忆，不强行给整张卡片设置唯一地点。
- 只有当多条来源确实指向同一地点，或用户明确表达地点时，才生成卡片级 `derivedPlace`。
- 旧图片/记录系统里的日期、地点能力可以继续复用，但不要直接继承旧卡片视觉。

## 摘要卡与全屏详情的关系

二者不是两套记忆，也不是不同的数据源，而是同一条记忆在不同场景下的不同呈现。

| 形态 | 场景 | 核心任务 | 信息密度 |
|---|---|---|---|
| Memory Summary Card | Memory Review 圆柱屏 / 记忆云水珠展开 | 快速看这条记忆是什么 | 中低，便于扫读 |
| Full Detail View | 点击摘要卡整体进入 | 查看完整来源、字段和历史 | 高，信息完整 |

设计结论：
- 不需要区分 Review 小卡和凝露卡，只需要一张统一的 Memory Summary Card。
- 它在不同位置出现：圆柱屏里是最近记忆摘要，星云里是水珠展开后的摘要。
- 位置、背景、进入动效可以不同，但卡片本体不分 mode。
- Full Detail View 才是完整信息视图。

### 聊天召回简化形态

当 Memory Card 被角色在聊天气泡里召回时，**去掉所有固定板块**（情绪角晕、状态块、Foot），只保留活动板块。理由：

- 用户已经在和 TA 对话，不需要重复操作入口（聊聊按钮）
- 离开了云团语境，情绪坐标不再重要
- 聊天上下文里的卡片应该更轻、更紧凑、不抢戏

这是同一张 Memory Summary Card 的轻量化版本，不开新数据结构。

## 当前系统混乱点

现在新旧卡片逻辑交叉，字段职责有重叠：

- SharedLife 抽取生成 `title`、`entity_type`、`patch.summary`、`patch.tags`、`source_message_ids`。
- SharedLife 当前 UI 会把 `title` 当作列表标题和详情页标题，把 `summary/details/...` 当作正文，把 tags/status/evidence/history 分块展示。
- 旧 timeline card / 图片记录更偏向“摘要 + 原文 + 标签 + 日期 + 地点”的记录卡。
- `title`、`summary`、`details/content` 容易表达同一件事，造成卡片里重复。
- 旧模板适合 Memex timeline，不适合直接作为新的对话记忆卡视觉和信息结构。

整理方向：

- 新记忆卡不再以“大标题 + 摘要”作为默认结构。
- 水珠需要短标识，卡片需要摘要/正文。
- 标签只做主题/归属，不替代类型。
- 当前状态只表达生命周期，不和摘要、时间混写。
- 原始对话和更新历史保留，但默认收起或放在详情较后位置。

## 内容类型候选

第一版不需要 30 多个视觉模板，也不按语义类型给每一类配独立 module。

**语义类型**（Event / Task / Plan / Fact / Emotion / Relationship / Media-Reading / Health 等）是后台理解层，进入 `tags`、`structuredFields`、`relatedEntities` 和聚合屏（健康屏、账本屏、兴趣屏等）。它们不直接决定卡片正面的视觉。

**呈现形式**（Text / Quote / Number / Table / Plan / Media）才是卡片正面的视觉语法。AI 抽取后按内容形式选择主模块，与语义类型解耦。

举例：

- 「看了一本书的感受」语义是 Media/Reading，呈现可能是 Text（写感受）+ 作品贴片，也可能是 Quote（摘抄一段）+ LinkAttachment。
- 「和朋友的关系变化」语义是 Relationship，呈现是 Text 或 Table + 人物贴片。
- 「最近的睡眠数据」语义是 Health，呈现是 Number + sparkline。
- 「一次情绪波动」语义是 Emotion，呈现是 Text 或 Quote，情绪强度由外壳层情绪坐标承载，不开新 module。

下表只说明语义类型在数据层与聚合屏的归属，不再作为视觉模板枚举。

| 类型 | 数据层作用 | 板块候选 |
|---|---|---|
| Event | 进入时间线、相关人物地点聚合 | Text / Media / Table |
| Task | 进入日程面（任务管理在那一面） | Table（只读任务符号 ☐ ☑） |
| Plan / Schedule | 进入日程聚合 | Table（时间/地点/事项） |
| Fact | 进入长期事实层 | Text / Quote |
| Emotion | 进入情绪坐标（外壳） | Text / Quote |
| Relationship | 进入人物聚合 | Text / Table + 引述对象 |
| Media / Reading | 进入兴趣聚合 | Text / Quote + 引述对象 / LinkAttachment |
| Health / Body | 进入健康聚合 | Number + sparkline / 进度条 |

## 借鉴旧模板的方式

旧卡片系统不要直接变成新记忆卡的 30 多种外壳，而应整理成可嵌入的活动板块或合并到固定板块。

旧 30+ 模板归并到新结构：

| 旧模板方向 | 新归处 |
|---|---|
| snapshot / gallery（首版图片，video 暂缓） | `Media` 板块 |
| quote / snippet | `Quote` 板块 |
| article / classic / compact / conversation | `Text` 板块 |
| metric / progress | `Number` 板块 + `进度条` 板块 |
| spec_sheet / transaction / ticket | `Table` 板块 |
| event / task / routine / procedure / duration | `Table` 板块（Plan 概念已并入 Table）|
| tickbox / checklist | `Table` 板块 + 只读状态符号 ☐ ☑ ⊘（任务管理归日程面）|
| link | `LinkAttachment` 板块 |
| place / map_focus / route_map | 进字段 / 标题 / 正文，不开新板块 |
| person / 人物头像 | `引述对象` 板块（仅已知人物）+ 聚合屏 |
| mood | 外壳层情绪角晕 |
| rating | 不复用——主观评分由用户自己用 Text / Quote 表达 |
| trend / sparkline | `sparkline` 板块（折线）|
| bar / radar / bubble / composition / contrast 等完整图表 | 不进 Memory Card，留给 Insight Card 的 `TrendChart` |

设计原则：
- 新卡只有统一凝露外壳：Memory Summary Card 和 Full Detail View。
- 板块分两类：**固定板块**（情绪角晕、状态块、Foot）和**活动板块**（标题、文字、Quote、引述对象、数字、表格、sparkline / 进度条、Media、LinkAttachment）。
- 一张卡片可包含多个活动板块，AI 按内容判断装配，按骨架规则排版。
- 聊天召回简化模式：去掉所有固定板块，只保留活动板块。
- AI 总结是默认主体，但图片、数值、引用等原始信息不能被压成纯文字消失。
- 只有在内容确实需要时，才出现对应板块。
- 语义类型（人物、作品、情绪、地点）不开新 module，由外壳层、引述对象、字段、聚合屏分别承担。

## AI 总结的呈现形式

`memorySummary` 不应被理解为“只能是一段文字”。它应该表示 AI 对来源材料的理解结果，而这个结果可以用多种形式呈现。

**范式**：Memory Card = 统一外壳 + 板块组装。AI 根据内容判断装配哪些活动板块，按骨架规则排版。一张卡片可以同时包含多个板块，不再「6 选 1」。

**活动板块清单**（按需装配）：

| 板块 | 适用内容 | 摘要卡中如何呈现 |
|---|---|---|
| 标题 | 结构化主体需要短归类（数字 / 表格 / 复杂组合） | 14px 顶部一行 |
| 文字段落 | 默认；普通事件、事实、情绪、偏好、关系、感受 | 一段叙述 |
| Quote | 用户原话、阅读 / 影视摘录 | 左侧细色条 + 略大字号 |
| 引述对象 | Quote / 感受引用已知人物或作品 | 11px 小行内归属 |
| Number | 健康、运动、睡眠、财务、进度的关键数值 | 42-46px 大字 + 单位 |
| Table | 订单、票据、预约、诊断报告、数字拆分、任务清单等 label-value | 多行标签-值 |
| Sparkline | 连续维度的趋势暗示 | 22-28px 高扁长折线 |
| 进度条 | 单值 vs 目标 | 6px 高横扁条 |
| Media | 照片为体验主体；首版仅图片 | 全宽预览 |
| LinkAttachment | 外部链接附件（小红书 / 文章 / 商品页） | 扁矩形 + 平台色块 |

**固定板块**（外壳层）：情绪角晕、状态块（仅异常）、Foot（tags + 聊聊）。

**不进 Memory Card 的形式**：完整 TrendChart（带轴、多 series）、柱状 / 饼图 / 雷达 / 散点等图表、可交互 Checklist、Timeline 视图。这些归 Insight Card 或专门功能屏（日程面）。

**聊天召回简化模式**：当 Memory Card 在角色聊天气泡里被召回时，去掉所有固定板块（情绪角晕、状态块、Foot），只保留活动板块，让卡片更轻、更紧凑，不重复操作入口。

设计结论：
- 摘要卡可以同时包含多个板块组合，不限 1 个主形式。
- 板块原子化：每个板块只承担单一职责，不嵌套子部分。
- 同一张卡通过板块组合表达不同内容，视觉差异来自板块本身的视觉签名。
- Full Detail View 是同一条记忆的更深展开，板块更全、信息更完整。

## 图片输入

图片不是一种总结形式，而是一种来源类型。识图之后仍需判断识别结果应该如何表达。

第一版建议：
- 信息型图片，如外卖订单截图、小红书帖子截图、票据、聊天截图：摘要卡展示识别后的结构化结论，再选择文字、数值、链接、引言、清单等形式。
- 照片分享，如生活照片、聚会照片、旅行照片、宠物/物品/场景记录：摘要卡可以直接呈现图片，因为图片本身就是记忆的主要体验。
- 如果图片只是证据，而不是体验主体，则不把原图放进摘要卡主体。
- Full Detail View 中展示完整图片、拍摄/导入时间、地点、原始说明、AI 识别结果。
- 如果一条整合记忆来自多张图片和多段对话，摘要卡只展示最能代表 AI 总结的形式；详情里显示全部图片来源。

图片卡的核心流程：
- 先判断图片是“信息来源”还是“体验主体”。
- 信息来源：展示识别后的总结形式。
- 体验主体：图片可以进入摘要卡展示。
- 地点和时间沿用旧卡片系统已有能力。

## 呈现形式选择器

替换旧模板库的核心是设计一个“呈现形式选择器”。

呈现形式是一套有限、稳定、可复用的视觉语法。

账本、健康、阅读、日程、关系、兴趣等业务语义进入后台字段、标签、关联实体和聚合屏；Summary Card 只选择少量稳定的视觉语法。

输入：
- AI 总结结果。
- 来源类型：文字、图片、截图、音频、外部数据等。
- 结构化字段：时间、地点、人物、数值、链接、作品、任务状态等。
- 用户偏好和历史纠错。

输出：
- 一个主要呈现形式。
- 可选的辅助字段。
- 置信度。

第一版活动板块及触发条件：

| 板块 | 什么时候用 | 摘要卡表现 |
|---|---|---|
| 标题 | 结构化主体需要短归类 | 14px 顶部一行 |
| 文字段落 | 默认形式；没有更强结构时 | 一段自然语言 |
| Quote | 原话/摘录本身最重要 | 左侧色条 + 17px 略大字 |
| 引述对象 | Quote / 感受引用已知人物或作品 | 11px 小行内归属 |
| Number | 数值是卡片核心 | 大数字 + 单位（原子化，不带子部分） |
| Table | label-value 多行结构（任意 value 类型） | 多行字段表 |
| Sparkline | 有 ≥3 个连续数据点，表达趋势 | 22-28px 扁长折线 |
| 进度条 | 单值 + 有目标 | 6px 高横扁条 |
| Media | 照片是体验主体（首版仅图片） | 全宽预览 |
| LinkAttachment | 可打开的外部链接 | 扁矩形 + 平台色块（0-N 个） |

固定板块（外壳层）：情绪角晕、状态块、Foot——不参与"按内容装配"判断，触发条件满足时自动出现。

规则：
- 低置信度时回退到 `文字段落`。
- 一张卡可以同时包含多个板块，不限制单选。
- 板块原子化：Number 只含主数值+单位，sparkline / 进度条 / 文字注释 / Table 都是独立板块。
- Quote 通常和"引述对象"绑定使用（如果引用了已知人物或作品）。
- 用户反馈"这个呈现不合适"后，记录偏好，减少同类错误。
- 截图、票据、订单、通知、帖子等信息型来源先做信息抽取，再分流到具体板块；信息抽取本身不作为板块。
- 主观评分（作品好坏、推荐度、喜爱度）不进任何板块，让用户在文字段落 / Quote 里自己表达。
- 情绪由外壳层情绪角晕承载，不开板块。
- 地点不开板块——有明确精确地点时进字段、标题或正文；城市级别不显示。
- 陌生网络发布者（小红书博主、评论区路人）不入引述对象，由 LinkAttachment 承担出处。
- 任务管理走日程面的可交互界面，Memory Card 上 Table 内的状态符号 ☐ ☑ ⊘ 只读展示，不可点击。
- 新业务语义优先复用已有板块。

骨架排版规则、装配示例、详细板块规范见 `MEMORY_PRESENTATION_MODULES.md`。

## Summary Card 与 Full Detail 字段分配

### Summary Card 显示

必须显示：
- `presentationModule`：AI 总结结果。
- `tags`：主题标签，少量显示。
- `chatAboutIt`：和 TA 聊聊/纠正这条记忆。

条件显示：
- `status`：仅当待确认、待同步、同步失败、需要用户确认等状态出现时显示。
- `LinkAttachment`：仅当链接对摘要卡有用时显示，提供明确打开入口。

不显示：
- 来源数量 / 来源类型。
- 全部原始对话。
- 来源时间线。
- 修订历史。
- 大段结构化字段。
- 编辑按钮。

点击整张卡进入 Full Detail View。

### Full Detail View 显示

必须显示：
- `presentationModule`：同一份 AI 总结结果。
- `allSources`：所有原始来源。
- `sourceMetadata`：附在每一条来源原始记录下的时间、地点、来源类型。
- `relatedEntities` / `relatedMemories`：相关人物、地点、作品、日程、其他记忆等。
- `edit`：编辑 AI 总结。
- `chatAboutIt`：和 TA 讨论修正。

条件显示：
- `structuredFields`：机器抽取/推导出的字段，只在有助于用户理解或确认时展示。
- `operationHistory`：放在最后，默认折叠。

### 水滴短文案与 tags 的区别

水滴短文案：
- 2-4 个字。
- 用于水珠上短暂显示。
- 目标是快速识别，不承担分类、不承担空间坐标。
- 不作为正式记忆字段；可由 `memorySummary` 运行时生成或缓存。
- 例：晚安、搬家、体检、论文。

`tags`：
- 主题标签。
- 用于筛选、归属、聚合。
- 可以有多个。
- 例：Health、Finance、Relationship、Reading。

空间坐标仍然由情绪/强度/时间等视觉规则决定，不由水滴短文案决定。
这样避免形成第二套标签系统。

### structuredFields 的意义

`structuredFields` 不是另一份 AI 总结，也不是必须裸露在摘要卡里的内容。

它是 AI/系统为了后续功能抽取出的机器可用字段，例如：
- 人物：谁参与了这件事。
- 时间：是否涉及具体时间或期限。
- 地点：是否有明确地点。
- 作品：涉及哪本书、哪部剧、哪个明星。
- 金额：是否涉及消费或收入。
- 任务状态：是否待办、完成、取消。
- 健康指标：睡眠、运动、体重等数值。

这些字段的用途：
- 支撑搜索、关联、日程、账本、健康屏、兴趣屏等后续功能。
- 支撑后台复核用户编辑后的影响范围。
- 在详情页帮助用户确认 AI 是否理解正确。

展示规则：
- `structuredFields` 默认不作为独立区块展示。
- 如果字段已经自然体现在 `presentationModule` 里，就不用重复展示。
- 如果字段对用户判断有帮助，可以在 Full Detail View 中以“识别信息 / AI 理解”折叠区展示。
- 如果只是后台索引或推理字段，可以不直接展示。
- Summary Card 不展示 raw structured fields。

## 统计图表和非文字形式

AI 总结不默认等于文字。

是否使用图表取决于内容是否有结构化数据：

| 内容 | 摘要卡 | 详情页 |
|---|---|---|
| 单次事件 / 情绪 / 偏好 | 文字、引言或情绪摘要 | 原文、标签、字段 |
| 任务 / 计划 / 日程 | Plan Block | 时间、步骤、提醒 |
| 健康 / 运动 / 睡眠 | 文字 + 关键数值 | 趋势、指标、历史图表 |
| 阅读 / 影视 / 追星 | 文字 + 作品/人物模块 | 引用、列表、相关作品 |
| 财务 / 交易 | 文字 + 金额模块 | 明细、趋势、地点 |
| 多张图片 | AI 识图结论 + 媒体来源标记 | 图集、地点、时间、识别结果 |

原则：
- Summary Card 不做复杂图表，最多展示关键数值、小型趋势、状态条、引用、链接或照片预览。
- Full Detail View 可以用图表、图集、时间线、表格。
- 图表必须服务数据理解，不为了视觉变化而出现。

## 设计方向

Memory Card = 统一凝露外壳 + 板块组装：

- **统一外壳**：Memory Summary Card / Full Detail View，凝露材质 + 圆角 + 阴影。
- **板块分两类**：**固定板块**（情绪角晕、状态块、Foot）和**活动板块**（标题、文字段落、Quote、引述对象、Number、Table、Sparkline、进度条、Media、LinkAttachment）。
- **板块原子化**：每个板块只承担单一职责，不嵌套子部分。AI 按内容判断装配。
- **骨架排版规则**（详见 `MEMORY_PRESENTATION_MODULES.md`）：
  - Tier 1 固定位：状态块顶 / 标题次顶 / Foot 底 / LinkAttachment 紧贴 Foot 上
  - Tier 2 邻近绑定：引述对象 + Quote/感受、数字 + 文字注释（并排）、数字 + sparkline/进度条
  - Tier 3 主体板块由 AI 按内容自由排
- **聊天召回简化**：在角色聊天气泡里召回 Memory Card 时，去掉固定板块，只保留活动板块。
- **统一操作**：聊聊（进对话）、点击卡片整体进 Full Detail View，详情中提供编辑。

这样既避免「全都长一样」，又不回到旧模板体系的碎片化。

## 外壳层固定板块

下列三类固定板块承担卡片基础结构，不参与 AI 内容装配判断：

| 固定板块 | 承载内容 | UI 位置 | 触发条件 |
|---|---|---|---|
| 情绪角晕 | 愉悦度 V × 唤起度 A 二维映射的色彩过渡 | 卡片左上角 radial 渐变 | 永远（低置信时几乎透明）|
| 状态块 | 异常状态：待确认 / 需复核 / 已撤销 | 卡片左上角胶囊，色块 + 文字 | 仅异常时 |
| Foot | tags（无 emoji 无 # 染色文字，上限 3）+ 聊聊按钮（主色填充） | 卡片最底部 | 永远（简化模式除外）|

地点、时间、人物 / 作品归属**不再走外壳层**：

- **地点**：进字段、标题或正文（精确具体地点才显示，城市级别不进 Memory Card）
- **时间**：进字段或来源 metadata，Summary Card 不强制显示
- **人物 / 作品归属**：用独立的「引述对象」活动板块承担（11px 小行内归属），不开大头像贴片

固定板块的作用：

- 解决「情绪、生命周期状态、分类、操作入口」这些卡片必备元素的统一表达。
- 让所有卡共享一套视觉语言，差异通过状态触发和情绪色彩传达。
- 与活动板块解耦：固定板块只表达卡片的「氛围 + 状态 + 入口」，活动板块表达内容。

## AI 自动评估的克制原则

云团需要 AI 给情绪坐标自动打分。这个坐标服务于水珠位置、记忆云分布和卡片左上角氛围色，不是对用户或对象的心理评价。

情绪坐标使用同一套二维结构：**愉悦度 Valence × 唤起度 Arousal**。视觉上落成四个象限：

| 象限 | 语义 | 视觉色 |
|---|---|---|
| V+ A+ | 兴奋、期待、被点亮 | 暖橙红 |
| V+ A− | 平静、满足、安稳 | 柔粉 |
| V− A+ | 紧张、焦虑、压力 | 紫红 |
| V− A− | 低落、疲惫、失去能量 | 深蓝灰 |
| 接近原点 | 中性、事实记录、情绪不明确 | 浅米中性 |

每条记忆可以带以下内部字段：

- `valence`：愉悦度，-1.0 ~ 1.0
- `arousal`：唤起度，-1.0 ~ 1.0
- `confidence`：AI 对坐标的把握，0.0 ~ 1.0
- `evidence`：支撑坐标的原文片段或来源说明
- `userOverride`：用户手动修正后的坐标

原则上 AI 可以打分，但必须克制、透明、可改：

- **默认低置信，弱信号不强行定位**。来源里没有明确情绪表达时，坐标置中且低置信，水珠在云团中央/边缘漂浮，不被错误情绪化。「无法定位」是合法状态。
- **永远不把分数显示成对对象的好坏评价**。不在卡片正面出现五星、N 分、AI 评价 = 高这类文字。坐标只作空间元数据，不翻译成判语。
- **不做对象级评分**。不给作品、餐厅、人物自动打分；用户的主观感受走 `Text` / `Quote`，由用户自己的话表达。
- **打分依据必须可看可改**。Full Detail View 展示坐标依据的原文片段；用户不直接改分数，而是通过统一的「聊聊」或「编辑」纠正 AI 理解。
- **AI 不主动赋予其他主观评价**。情绪坐标之外的主观字段（好坏、推荐度、喜爱度）一律留空，由用户表达。

Summary Card 只使用左上角情绪角晕表达氛围，不显示数值、不显示情绪词；Full Detail View 可以在「AI 理解 / 识别信息」折叠区里展示依据，但不为情绪单独设置修正控件。所有信息偏差统一通过「聊聊」或「编辑」处理。用户修正后，云团位置和卡片角晕都跟随更新。

这条原则同时管住几件事：情绪坐标不会变成卡片正面的标签噪音，不会自动给作品或人打分，也不会在依据不足时把普通记录强行情绪化。

## 与旧模板的关系

旧模板可以作为内容模块参考，但不直接作为新记忆卡片的视觉语言。

建议：
- 保留旧模板用于兼容旧 card / insight 场景。
- 新增 Here I Am 记忆卡体系，服务 Memory Summary Card 和 Full Detail View。
- 逐步把适合的旧模板能力抽象成内部模块，而不是把旧样式搬进新 UI。
